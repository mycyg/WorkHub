## 缺陷清单

### BUG-01 [P0] `cargo tauri build` 产出的正式 `.app` 验签失败并被系统杀死

- 位置：macOS release bundle / `client-tauri/src-tauri/target/release/bundle/macos/WorkHub.app`
- 复现率：必现
- 步骤：执行正式 `cargo tauri build`；随后执行 `codesign --verify --deep --strict --verbose=2 WorkHub.app`、`spctl --assess --type execute --verbose=4 WorkHub.app` 或直接运行 bundle 内 executable。
- 预期：构建成功的正式包可验签并启动。
- 实际：`codesign` 报 `code has no resources but signature indicates they must be present`；`spctl` 报 `bundle format unrecognized, invalid, or unsuitable`；bundle executable 立即被 SIGKILL（exit 137）。包内没有 `_CodeSignature`，只有 linker ad-hoc 标记。
- 根因隔离：裸 `target/release/workhub-client-tauri` 可运行；复制 `.app` 后执行本地 `codesign --force --deep --sign -`，验签通过且 Computer Use 可完整打开 Spotlight、工作台、聊天。因此问题位于正式 bundle 的资源签名/打包门禁，而不是应用业务逻辑。
- 风险：构建命令 exit 0 给出假阳性；当前 DMG 内应用不可作为可交付物。
- 建议：修正 Tauri macOS bundling/signing，并在正式构建门禁加入 `codesign --verify --deep --strict`、`spctl`（可按发布策略配置）及从 bundle 路径启动的 smoke；不能只验证裸二进制。

### BUG-02 [P1] 无 Key 模式仍构造 LLM 客户端并向外部供应商发请求

- 位置：`packages/agent/src/providers/registry.ts:35-49`；`apps/api/src/services/conversation-turns.ts:1002-1023,1177-1204`
- 复现率：必现
- 前置：独立数据库 `workhub_nokey_0715`，API 不带任何 LLM 环境变量，health 显示 `ai_provider_configured=false`。
- 步骤：创建协同会话与用户消息，调用 `POST /conversations/:id/turns`。
- 预期：在调用供应商前 fail fast，返回明确的 `AI 服务未配置` 语义；不产生外网请求。
- 实际：registry 的 `isConfigured()` 会返回 false，但 `get()` 不检查配置，仍以空 Key 创建 transport。服务真实请求 DeepSeek 后收到 401，再被 `createTurn` 映射为泛化的 HTTP 500：`conversation_turn_failed / 这一轮 Cuu 没接上，请再试一次。`
- 影响：违反无 Key 自托管语义和 fail-fast 原则，也让诊断信息只存在服务端 warn 中，前端无法区分未配置与供应商故障。
- 建议：在 provider registry/服务 wiring 的唯一入口强制拒绝未配置 provider，使用稳定的 typed error（建议 503）；turn 路由明确映射成部署指引文案，且测试断言没有 transport 调用。

### BUG-03 [P1] 桌面 WebView 与 Rust SSE 使用不同服务端/Token 配置源

- 位置：`apps/desktop-webview/src/browser.ts:128-160`；`apps/desktop-webview/src/workbench/boot.ts:23-80`；`client-tauri/src-tauri/src/main.rs:1114-1139`
- 复现率：必现
- 步骤：以 `WORKHUB_SERVER_URL=http://127.0.0.1:18787` 和独立无 Key API Token 启动 app，同时 WebKit localStorage 中保留之前 8787 的 `workhub_api_base/client_token`。
- 预期：整套桌面应用（WebView API、聊天 SSE、Rust 壳 SSE）使用同一服务和身份。
- 实际：Rust SSE 读取 env/server config；WebView 只读 localStorage 或默认 8787。WebView 随后把旧 localStorage Token 调 `set_client_token` 推回 Rust，覆盖 env Token。本轮日志显示期望的新 Token 被旧 Token 尾号替换，UI 继续展示 8787 的 Key 数据。
- 风险：同一窗口的 HTTP 与 SSE 可连接不同后端/身份；跨端一致性、登出、安全隔离及无 Key桌面验收都不可信。
- 建议：由 Rust 壳暴露单一、只读的 runtime connection config 给 WebView；明确 Token 归属与版本，服务地址和身份原子切换；禁止 localStorage 在未核对 server identity 时覆盖壳层配置。

### BUG-04 [P1] 审批落定消息已入库但没有 `conversation.message.created` 实时事件

- 位置：`apps/api/src/routes/proposals.ts:161-209`；`packages/db/src/repositories/action-cards.ts:413-464`
- 复现率：按代码路径必现
- 预期：审批通过/打回/合入后，正在打开来源群聊的所有客户端立即看到“落定行”。
- 实际：notifier 通过 `postSystemMessage` 只插入 DB；随后仅在存在行动卡血缘时 publish `conversation.action_card.updated`。没有为新 system message publish `conversation.message.created`。聊天事件处理只会刷新卡片状态，不会凭空取得刚插入的消息。
- 影响：手册 §6.6 的“群聊出现落定行”只能在刷新/重连/补洞后出现，实时闭环不成立。且整个 notifier 被 best-effort 包装，失败仅 warn、无重试/补偿。
- 建议：让消息创建与 outbox/event 同事务，或复用统一的 persist-and-publish 服务；加入两客户端开着会话时审批落定的集成测试，不能只测 renderer。

### BUG-05 [P1] 已读请求失败后，本次 seq 会被永久认为“已发送”

- 位置：`apps/desktop-webview/src/workbench/chat/view.ts:1183-1201`
- 复现率：网络请求失败时必现
- 预期：PUT `/read` 失败应保留可重试状态、记录可观察错误，并在重获焦点/恢复网络后重试。
- 实际：请求前先把 `lastSentReadSeq=seq`，随后 `.catch(() => undefined)`；失败后同 seq 被 `seq <= lastSentReadSeq` 永久挡掉，除非出现更高 seq。
- 影响：读游标和未读分割线在断网/瞬态 5xx 后长期不一致，且完全无日志。
- 建议：拆分 attempted/acked cursor；仅在服务端成功后推进 ack，失败回滚或排队重试，并记录 conversation/seq/error 的结构化诊断。

### BUG-06 [P1] 登出成功与 Rust SSE Token 清除存在竞态，旧连接可继续存活

- 位置：`apps/desktop-webview/src/spotlight/views/settings.ts:731-760`；`client-tauri/src-tauri/src/main.rs:479-501`；`client-tauri/src-tauri/src/sse_worker.rs:91-137`
- 复现率：服务端 logout/壳 invoke 失败或 SSE 正处于 open 时可复现
- 预期：登出必须确认服务端吊销和壳层 Token 清除，并立即终止/重连现有 SSE。
- 实际：前端把 `logout()` 失败吞掉，清 localStorage 后对 `set_client_token("")` 也 fire-and-forget；Rust 空 Token 分支在 `notify_waiters()` 前直接 return；SSE worker 只在 open stream 结束后才进入监听 token-change 的 select，当前连接不会被取消。
- 影响：UI 显示已登出时，后台旧身份 SSE 仍可能继续收事件；错误不可观察。
- 建议：登出使用有确认的状态机；清 Token 必须通知并取消现有 response pump；失败时不应假装完成，需保留可恢复提示与日志。

### BUG-07 [P2] 自动化验收契约漂移，导致门禁不能代表当前产品

- `qa:r4-web-product-shell-baseline`：home loader 新增 `listProjects()`，脚本 fake client 没同步，稳定失败为 home error；route 单测 fake 已包含该方法。
- `qa:r5-10-real`：脚本仍假设首轮澄清走自由文本；当前服务按 R10 设计在有候选时返回 `single_choice`，真实 Key评测在 LLM 调用前失败。
- R14 chat/search smoke 默认共享 scratch DB；chat 先写入“完播率”消息后，search smoke 的固定命中数从 1 变 2。换全新隔离 DB 后 search smoke 通过。
- `pnpm verify` 会改写 tracked schema/audit 文件；Chrome live QA 失败还会删除一批 tracked 截图/报告。门禁不具备 dry/clean 性。
- 建议：测试 fixture 复用生产接口契约；每个真库 smoke 自建唯一 DB/schema 并自动清理；验证命令结束后强制 `git diff --exit-code`；生成审计资产与日常 verify 分离。

### BUG-08 [P2] 测试手册路由与产品 Single Source of Truth 不一致

- 复现率：必现
- 手册失败路径：`/inbox`、`/health`、`/cost`、`/agents`。
- 代码真实路径：`/notifications`、`/dashboard/health`、`/dashboard/cost`、`/dashboard/agents`（`apps/web/src/routes.ts:176-216,550-564`）。
- 影响：按最新 handoff 文档验收必然得到四个 404；新人会误判产品页面缺失。
- 建议：明确要保留兼容 alias/redirect，还是修正文档；路由清单应由 route registry 生成并在 CI 校验，避免双重维护。

### BUG-09 [P2] Chrome/CDP live QA 吞掉浏览器 stderr，启动失败不可诊断

- 位置：`apps/web/src/chrome-launch.ts:112-143`
- 复现率：本机 Chrome 150.0.7871.124 下稳定
- 实际：Chrome 子进程存活但 remote debugging 端口从不监听，QA 最终只有 `Timed out waiting for Chrome CDP target: TypeError: fetch failed`。launcher 使用 `stdio: "ignore"`，最关键的 Chrome 启动诊断被丢弃。
- 对照：同一 Web 服务用 Safari + Computer Use 可正常验收；headless `--dump-dom` 脚本也可工作，因此不是 Web 服务宕机。
- 建议：捕获并限长保存 stderr、启动参数、Chrome version、exit/signal、端口探测过程；超时报告附诊断文件。
