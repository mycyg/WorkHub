## 1. 执行摘要

WorkHub 把现有「需求管理大师」从"人干活、AI 打下手"的工具,进化为"**AI 干活、人把关**"的 AI-native 协作平台。

核心是一次**角色反转**与一个**一人两顶帽子的 Agent**:
- **默认态:AI = 工人**,直接产出交付物(文档 / 分析 / 方案 / 代码)。
- **受阻态:AI = 项目经理**,当 ① 不合格 ② 用户不满意 ③ 用户明确不让 AI 干 时,AI 不硬扛,转而组织人完成(派活、排期、提醒、盯进度、再审)。
- **切换条件 = 升级条件**,由**置信度 / 风险分级**裁定。

外层包裹一套**去 git 黑话的 GitHub 协作模型**:协作者各有"分支",改动以"提议"形式提交,负责人审过才"合并到 main";用户看到的是「AI 拟好了,确认?」而非 merge / 冲突。入口是**桌面宠物 + web**,Agent 几乎能操作所有功能,小白也能用。

**为什么现在做、为什么能做成**:现有产品的 deliver→负责人「通过/打回」循环已是 PR-review 雏形;`auto_agent` 已是能产出交付物的 tool_use Agent;`llm_review`、`RevisionRequest`、`spec_watch` 等零件齐备。WorkHub 是把这些零件串成自治闭环并补齐三块护城河(多用户审批路由、业务对象合并、组织治理)。opencode 源码研究证实这套"headless agent daemon + 分层 permission + 升级"架构有成熟先例。

## 2. 背景与问题

### 2.1 现状(需求管理大师 today)
- 局域网、免登录(昵称即身份 + 设备令牌)的需求管理中台。
- 两空间:**派活/Dispatch**(浏览器可用)vs **接活/Work**(桌面客户端专属,服务端校验设备令牌)。
- 闭环:AI 澄清需求 → 入池 → 认领 → 交付 → 负责人验收(通过/打回)→ 可派生后续。
- 已有:项目网盘(版本/回收站/评论触发 LLM)、会议纪要→洞察→需求草稿、grep 知识库(无向量库)、排期、通知、`auto_agent` 沙箱执行。
- 栈:FastAPI + SQLAlchemy + **SQLite(必须单 worker)**;web=React/Vite;桌面=Tauri v2 + Rust;LLM=DeepSeek(Anthropic 兼容端点);ASR/TTS=GPU 服务。

### 2.2 痛点 / 缺口
1. **AI 只"建议",不"干活"**:助手只能答疑 + 起草,`auto_agent` 仅对 file-only 需求可选启用——AI 没有占据默认执行路径。
2. **人是默认劳动力**:每步都要人推进,小白上手成本高。
3. **协作是线性的**:有版本号、有验收,但没有"分支 / 提议 / 合并"的并行协作心智。
4. **双向同步未做**:客户端仅下载,`sync.rs` 双向是占位。
5. **打扰方式原始**:右下角弹窗 / 托盘,缺一个有人格、能对话、能代操作的入口。
6. **并发天花板**:SQLite 单 worker——多 Agent + 多人并发撑不住。

### 2.3 洞察
> 现有的「deliver→通过/打回」其实就是 PR review。我们已经造了"业务版 GitHub"的脊梁骨,只是没命名,也没让 AI 坐上驾驶位。WorkHub = 给它命名 + 让 AI 默认驾驶 + 补齐多人协作与治理。

## 3. 愿景、定位与非目标

### 3.1 北极星
**让一个团队里"绝大多数事"由 AI 默认完成,人只在 AI 做不好 / 做不了 / 不该做时介入;且无论 AI 还是人改动,都经"提议→审批→合并"汇入单一可信源(main)。**

### 3.2 定位
- 对内一句话:**业务版 GitHub**。
- 对外一句话:**会自己干活的 AI 工作平台**。

### 3.3 非目标(v1 明确不做)
- 不做通用 IM / 文档协同编辑器(不与飞书/Notion 正面竞争编辑体验)。
- 不做向量检索(延续 grep + 强制引用的知识范式)。**[决策]**
- 不做"AI 替你做线下 / 需专业资质判断的事"(L2 只覆盖数字可交付物)。
- v1 不追求多租户公网 SaaS(见 D-3)。

## 5. 核心理念(产品宪法)

这五条贯穿所有功能,任何设计冲突以此为裁决基准:

1. **AI-native 默认驾驶**:每个环节默认"AI 提议 / AI 执行",人确认。
2. **一人两顶帽子**:AI 默认是工人;受阻即变项目经理。**切换条件 = 升级条件**。
3. **人是审批者 + 异常处理者**,不是默认劳动力。
4. **去黑话**:对用户永远是「AI 拟好了,确认?」,绝不暴露 merge / 分支 / 冲突 / 置信度阈值等术语。
5. **AI 绝不静默改生产态**:任何 AI 改动都可解释(为什么)、可回滚(快照)、经审批才汇入 main。(延续现有 `models.py:291` 的法律,升级为全局默认)

### 7.1 WorkItem 状态机(演进)
```
intake → ai_clarifying → spec_ready
      → ai_working(工人模式)
          ├─ confidence: high  → auto_proposal → (策略)直接合并 / 抽检
          ├─ confidence: mid   → human_spotcheck → 合并 / 打回
          └─ confidence: low / high_risk / blocked → escalated
      → escalated → pm_mode(经理模式:派活→人做→提议)
      → in_review(负责人审 Proposal)
          ├─ approve → merged(汇入 main)
          └─ reject(带理由)→ ai_working(回灌纠偏)或 reassign
      → merged → (可派生后续) / done
      → cancelled
```

## 8. 核心机制详述(事无巨细)

### 8.1 AI 工人引擎(L2,默认态)
- **目标**:让"产出交付物"成为 AI 的默认动作,而非人的。
- **执行循环**:借鉴 opencode `runLoop` —— 单循环驱动,每步增 step、装配工具+上下文、调模型、按控制信号 `continue/stop/compact/escalate` 分支。**完成判定 = AI 不再请求动作**(产出最终交付而非再调工具),而非显式 flag。
- **工具系统**:最小契约 `{id, 描述, 参数 schema, execute}`;注册表按"当前 actor 权限"过滤模型可见的工具菜单;schema 校验失败 → 回灌"请改输入"的可恢复错误(不崩)。复用 `auto_agent` 现有工具(list/read/write/mkdir/move/delete/run_command/zip/submit)。
- **沙箱与预算**:延续 `auto_agent` 的沙箱(文件/大小上限、命令白名单、rlimit)+ 预算(MAX_TURNS、超时)。**[决策]** 每个 AgentRun 必须有硬预算上限。
- **可回滚**:借鉴 opencode 的"每步 git 快照"——AI 对业务数据的每次副作用都生成快照,任何步骤可 revert。**[决策·安全红线]**

**FR-WORKER-001 (P0)**:系统支持将一个 WorkItem 默认派给 AI 工人执行,无需人工逐步干预。
**FR-WORKER-002 (P0)**:每次 AgentRun 产生完整 trace(每步动作 + 工具输入输出)可供人审。
**FR-WORKER-003 (P0)**:AgentRun 超预算时,强制产出「已做 / 未做 / 下一步」结构化交接件(借鉴 opencode `MAX_STEPS`),而非静默截断。
**FR-WORKER-004 (P0)**:AI 的每次副作用动作可回滚到执行前快照。

### 8.2 升级 + 置信度/风险分级(命门)
- **置信度来源 [开放·待标定]**:候选 = ① AI 自评分(模型自报)② `llm_review` 判分 ③ 验收清单逐条命中率 ④ 历史校准(同类任务过往通过率)。**[建议]** v1 用 ②+③ 为主,①为辅,④随数据积累接入。
- **风险评分**:任务影响面(可逆性、对外性、金额/合规敏感度、影响人数)。**[开放]** 风险维度需与业务方共定。
- **分级裁决**:
  | 档 | 条件 | 处置 |
  |---|---|---|
  | 高置信 + 低风险 | review 过 + 清单全过 + 低风险 | **直接生成 Proposal,按策略可自动合并 main** |
  | 中等 | 部分不确定 / 中风险 | **生成 Proposal,转人工抽检(快速 通过/打回)** |
  | 低置信 / 高风险 / 卡住 | review 不过 / 高风险 / doom-loop / 超预算 | **升级:转项目经理模式找人** |
- **三个升级触发器(对应现有零件)**:
  1. **不合格** ← `llm_review` 判分不过(`auto_agent.py:544`;评审提示词 `REVIEW_SYSTEM` 在 `:535`)。
  2. **用户不满意** ← 负责人打回(`RevisionRequest`)。借鉴 opencode:**打回必须带理由,理由回灌给 AI 触发自我纠偏**,而非停摆。
  3. **用户明确不让 AI 干** ← 新增"人工保留"开关(WorkItem / 项目 / 用户 三级)。
- **额外自动升级信号(借鉴 opencode)**:**doom-loop**(连续 N 次相同动作判"卡住")、**预算耗尽**。

**FR-ESC-001 (P0)**:每次产出生成 ConfidenceRecord(置信度 + 风险 + 分级裁决 + 依据),对用户以"人话"呈现(如"我比较有把握,但建议你扫一眼"),不暴露数值阈值。
**FR-ESC-002 (P0)**:三个触发器中任一命中即创建 EscalationEvent 并切换 WorkItem 至经理模式。
**FR-ESC-003 (P0)**:打回必须带理由;理由作为上下文回灌,AI 在同分支续做而非重来。
**FR-ESC-004 (P1)**:doom-loop / 超预算自动升级。
**FR-ESC-005 (P1)**:"人工保留"开关支持 WorkItem / 项目 / 用户 三级配置。

### 8.3 AI 项目经理模式(L1,受阻态)
- **激活**:EscalationEvent 触发。
- **职责**:① 据 EscalationEvent 交接件理解"卡在哪" ② 智能派活(8.4)选合适的人 ③ 拆解 + 排期 + 设提醒 ④ 盯进度、催办 ⑤ 人产出后,AI 再审并协助生成 Proposal。
- **关键**:经理模式下 AI 不静默替人决策——派活、催办都是"提议→人确认"。

**FR-PM-001 (P0)**:升级后 AI 自动生成"为什么升级 + 建议谁来做 + 计划"的可读简报。
**FR-PM-002 (P1)**:AI 自动排期并按计划设置提醒/催办。
**FR-PM-003 (P1)**:人完成后,AI 协助把产物整理为可审的 Proposal。

### 8.4 智能派活(旗舰样板)
- **输入**:UserProfile(技能自述 + 自我介绍)+ CollaborationGraph(既往协作 + 命中率 + 当前负载/可用度)+ WorkItem 画像。
- **输出**:**提议** 负责人 + 协作人(含"为什么推荐他"的理由),**人确认 / 调整**。
- **冷启动降级 [建议]**:无历史时 →(a)只凭自述技能粗匹配 +(b)**展示推荐理由让人决定**,而非"AI 替你定";随数据积累再增强。
- **护栏**:负责人可一键改派;AI 推荐错被纠正后写入反馈,改进后续。

**FR-STAFF-001 (P0)**:新用户 onboarding 必填"擅长什么 + 自我介绍"。
**FR-STAFF-002 (P0)**:有新 WorkItem 时,AI 提议 负责人 + 协作人 + 推荐理由。
**FR-STAFF-003 (P0)**:推荐必须可被人一键确认或调整。
**FR-STAFF-004 (P1)**:冷启动时降级为"解释式推荐";有历史后引入命中率加权。
**FR-STAFF-005 (P2)**:负责人对推荐的纠正回流,用于改进模型。

### 8.5 协作:分支 → 提议 → 合并(去黑话)
- **心智映射(对用户隐藏术语)**:
  | 内部(git 心智) | 用户看到的 |
  |---|---|
  | branch | "我的工作副本 / 草稿" |
  | commit/diff | "改动" |
  | open PR | "提交给负责人确认" |
  | review/approve | "确认" / "打回(说原因)" |
  | merge to main | "采纳 / 汇入正式版" |
  | conflict | "和别人的改动撞了,AI 给了合并方案,选一个" |
- **并行**:多协作者(及多 AI 工人)各在自己分支,互不阻塞。
- **冲突**:同一对象并发改动 → **AI 调解**:自动给出合并建议,人择一/微调。**[开放]** 业务对象的合并语义(文档 vs 结构化记录)需分类型定义——这是 opencode 未解、WorkHub 必须啃的护城河之一。

**FR-COLLAB-001 (P0)**:每个协作者/AI 工人对 WorkItem 的改动在独立分支进行。
**FR-COLLAB-002 (P0)**:改动以 Proposal 提交,负责人 通过→合并 main / 打回带理由。
**FR-COLLAB-003 (P1)**:并发改动冲突时,AI 生成合并建议供人选择。
**FR-COLLAB-004 (P0)**:全程 UI 不出现 git 术语。

### 8.6 审批与权限(RBAC + 分层策略,借鉴 opencode)
- **审批 = 阻塞原语**:任何工具在"该决策那一刻"可 `ask` 人,阻塞至回复。
- **分层策略**:`org → workspace → role → session` 合并的 allow/deny/**ask(默认就问)** 通配规则。
- **学习**:"永远允许"沉淀成自动规则(逐步减少打扰)。
- **审批路由(护城河,opencode 没有)**:决定**谁该批**(按角色/负责人/项目),未响应的**超时 SLA**,可委派,**按身份审计**。
- **回灌**:拒绝带理由 → 作为下一步上下文喂回 AI。

**FR-PERM-001 (P0)**:支持分层 allow/deny/ask 权限策略,未匹配默认 ask。
**FR-PERM-002 (P0)**:审批请求按角色/负责人路由到正确的人。
**FR-PERM-003 (P1)**:审批支持"永远允许"沉淀规则 + 超时 SLA + 委派。
**FR-PERM-004 (P0)**:所有 AI 动作按身份写入 AuditLog,可追溯、可回滚。

### 8.8 README = 需求规格展示页
- **理念**:每个 WorkItem / 项目有一个活的 README,即"需求明确文档",随澄清/交付自动更新。
- **作用**:单一可信源的门面;AI 与人都对照它工作与验收。

**FR-SPEC-001 (P1)**:每个 WorkItem/项目有自动维护的 README 规格页。
**FR-SPEC-002 (P2)**:规格页变更走提议→合并(与内容协作一致)。

### 8.9 桌面宠物入口(L4)
- **替代**:右下角弹窗 / 托盘菜单 → 一个有人格、可对话的桌宠。
- **能力**:点击出对话框;自然语言指令 → Agent 代操作几乎所有功能;主动但有节制地提醒(任务/升级/催办)。
- **小白友好**:全程人话,不要求学习功能位置。
- **架构**:桌宠与 web 都是同一 headless agent daemon 的瘦客户端(借鉴 opencode `createOpencode` + SSE 事件流)。

**FR-PET-001 (P1)**:桌宠常驻,点击出对话框。
**FR-PET-002 (P1)**:用户自然语言指令可驱动 Agent 操作功能(派活、查状态、提交等)。
**FR-PET-003 (P1)**:提醒/升级以桌宠呈现,替代右下角弹窗。
**FR-PET-004 (P2)**:打扰频率/时段可由用户设边界。

### 8.10 可解释性与知识
- 延续 grep + **强制引用**;AI 的每个判断(为何推荐此人、为何升级、为何判不合格)都给可读理由 + 证据。
**FR-EXPLAIN-001 (P1)**:AI 的派活/升级/判分决策均附人话理由 + 证据引用。

## 9. 关键用户旅程(端到端)

**J1 — 新用户 onboarding**:进入 → 填"擅长什么 + 自我介绍" → 桌宠自我介绍并演示一句话指令 → 完成。

**J2 — 一条需求的"AI 默认干完"主路径**:
口头/文字提交 → AI 澄清(谁/何时/验收/负责人/DDL)→ 生成规格(README)→ **AI 工人执行** → 产出 + ConfidenceRecord → 高置信低风险:**自动 Proposal → (策略)合并 main** → 通知提交者完成。

**J3 — 升级路径(AI 做不好)**:
AI 工人执行 → 低置信/高风险/卡住 → **EscalationEvent** → AI 转**项目经理** → 智能派活提议负责人+协作人 → 人确认 → 人做(AI 辅助)→ 整理为 Proposal → 负责人审 → 合并。

**J4 — 用户不满意(打回纠偏)**:
负责人看 Proposal → 打回 + 写原因 → 原因回灌 → AI 在同分支续做 → 重新提交。

**J5 — 多人并行协作**:
两位协作者各在分支干 → 分别提议 → 负责人逐个审 → 合并;若撞车 → AI 给合并方案 → 人择一。

**J6 — 小白用桌宠**:
点开桌宠 → "帮我把上周那个活的进度问一下并催一下" → Agent 查状态 + 起草催办 → "确认?" → 用户点确认 → 完成。

## 11. 技术架构方向(供 planning 展开)

- **核心架构 [决策]**:**headless agent daemon + OpenAPI 契约 + SSE/WS 事件流 + 类型化客户端**(借鉴 opencode)。桌宠 / web / 未来移动端皆瘦客户端;权限询问、进度、结果皆为流上事件。
- **LLM 抽象 [决策]**:统一 provider 注册表,DeepSeek-via-Anthropic 作为一个 provider 接入,系统其余保持模型无关;低风险任务可路由更便宜模型(成本治理)。
- **数据底座 [建议·待确认 D-2]**:由 SQLite 迁移到 **PostgreSQL**(支撑并发、多 Agent、行级锁/乐观锁以做业务对象合并);保留软删除范式。
- **新仓策略 [建议·待确认 D-1]**:**新建仓库,迁移现有 FastAPI+Tauri 地基并重构为 daemon+clients**,而非从零重写——复用已验证的状态机、`auto_agent`、`lifecycle`、`spec_watch` 与安全模型,降低风险。

## 13. 成功度量

- **自治率**:无人执行即完成的 WorkItem 占比(北极星)。
- **升级精准度**:该升级时升级、不该时不升级(precision/recall)。
- **信任**:合并后回滚率、打回率(越低越好)。
- **效率**:需求平均交付时长下降。
- **小白激活**:onboarding 完成率、首个 AI 任务成功率。
- **成本**:每条已交付需求的 AI token 成本。

## 14. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **信任崩塌**(AI 过度自信发垃圾)| 用户退回手动,产品死 | 保守分级、中档强制抽检、快照回滚、透明置信度+理由 |
| **冷启动**(无历史、自述不准)| 派活失准 | 降级"解释式推荐"、人可改派、随数据校准 |
| **成本失控**(AI 当默认劳动力)| token 烧穿 | 三级预算/配额、低风险用廉价模型、硬预算上限 |
| **安全**(AI 自治改业务数据 / 上云)| 数据/合规事故 | 沙箱、权限策略、高风险人工门、审计、回滚;上云前重审威胁模型 |
| **范围蔓延**(全都要)| 永远做不完 | 严格分期,P1 旗舰先证明价值 |
| **护城河三难**(审批路由/对象合并/治理 opencode 未解)| 最难、最易低估 | 列为 P3/P5 深设计专题,提前预研 |
