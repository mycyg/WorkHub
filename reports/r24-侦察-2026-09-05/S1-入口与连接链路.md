## 2. API 地址怎么决定

**默认值**：`http://127.0.0.1:8787`（`apps/desktop-webview/src/desktop-api-base.ts:13-15`，端口取 `@workhub/config/ports` 的 `defaultPorts.api`）。

**localStorage 键**：`workhub_api_base`（`desktop-api-base.ts:11`）。

**校验规则**（`normalizeDesktopApiBase`，`desktop-api-base.ts:18-38`）——拒绝：
- 空/`trim` 后为空（:19-22）；
- `new URL()` 解析失败（:23-28）；
- 协议不是 `http:`/`https:`（:29-31）——`javascript:`、`data:`、`file:` 全拒；
- URL 里带用户名/密码/查询串/hash（:32-35）。
归一化：去末尾斜杠，保留 `origin + pathname`（:36-37）。读取端非法值按「未配置」回落本机默认（:41-51）。

**界面里能不能设**：**只有一个入口，而且它基本进不去**——离线卡的「打开设置 → 服务器地址」（`desktop-offline-card.ts:67` 的表单、:73-106 的接线）。全仓 `workhub_api_base` 的消费点只有 `browser.ts:68-69,244,270,405`、`workbench/boot.ts:39-41,266`、`spotlight/views/drive.ts:45`——**Spotlight 设置视图、工作台设置页里都没有服务器地址字段**。而离线卡只在 `bootSpotlight` 的 `catch` 里渲（`browser.ts:395-397`），详见断点 E-02：正常的「连不上」根本不抛异常。

**三窗如何共享**：同源 localStorage 天然共享，但**读取只在各自 boot 时发生一次**（`browser.ts:270`/`:405`、`workbench/boot.ts:266`）。离线卡改完地址只 reload 自己那个窗（`desktop-offline-card.ts:104-105` → `input.reload` ← `browser.ts:251` = `window.location.reload`），另外两窗要等各自重启才跟上；且没有任何跨窗广播（对比：登出有 `workhub-logged-out` 广播，`settings.ts:1343-1349` / `workbench/boot.ts:217-228` / `pet-surface.ts:1737`）。

**Rust 壳层还有第二份、完全独立的服务器地址**：
- `WorkHubShellConfig.server_url`，默认同样是 `http://127.0.0.1:8787`（`config.rs:19-26`），来源是 OS 配置目录下的 `workhub-shell-config.json`（`main.rs:1849-1853,1855-1867`）+ 环境变量 `WORKHUB_SERVER_URL`（`config.rs:5,92-94`）。
- SSE 订阅 URL 由它拼（`sse.rs:133-147` → `http.rs:20-28 daemon_url`），且在 `.setup()` 里**按值捕获一次**（`main.rs:1978 spawn_default_shell_sse_workers(app.handle().clone(), shell_config)`）。
- 全仓 `#[tauri::command]` 清单里**没有任何 `set_server_url`**（`main.rs:231-1757` 全部命令；注册清单 `main.rs:1888-1908`）。
→ webview 的 api base 和壳层 SSE base 可以永久分叉：用户在离线卡里把地址改成 `https://workhub.example.com`，Rust 的通知/Cuu 推送流仍然死打 `127.0.0.1:8787`。

### 2.1 CSP connect-src：SA-01 点名的硬阻断——结论 = 会拦死，两位用户都拦死

`tauri.conf.json:16`：

```
default-src 'self'; connect-src 'self' ipc: http://ipc.localhost http://127.0.0.1:* http://localhost:* ws://127.0.0.1:* ws://localhost:*; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; object-src 'none'; frame-ancestors 'none'
```

- `'self'` 在打包后 = `tauri://localhost`（macOS 自定义协议源），不含任何外部主机。
- `http://192.168.1.10:8787`（甲）：不匹配 `127.0.0.1:*`，也不匹配 `localhost:*` → **被拦**。
- `https://workhub.example.com`（乙）：`connect-src` 里连 `https:` 都没有 → **被拦**。
- 仓库自己就是这么写的：`desktop-api-base.ts:6-7`「即使存进了非回环地址，打包后的 webview 也连不出去」；台账 `reports/审查台账-2026-08-19.md:52,547`（DSK-05：「打包后连远端 https 后端的取舍已注释+待评估」）；`reports/r23-侦察-2026-09-05/A-产品与集成度缺口.md:24` 同一结论。
- **为什么开发期从没暴露**：`tauri.conf.json:9` 的 `devUrl` 是 `http://127.0.0.1:1420`，而 `apps/desktop-webview/vite.config.ts:11-14` 把 `/api` 代理到 `http://127.0.0.1:8787`——dev 态永远只连回环，且 dev 由 Vite 服务页面、CSP 注入路径与打包态不同。这个缺陷只在真正的 `.app` 里发作。

结论一句话：**`connect-src` 白名单只有回环 + ipc，甲的局域网 IP 和乙的公网 https 都连不出去；这是打包后的死锁，必须在 CSP 层解决，前端改地址救不了。**

## 3. 登录

### 3.1 昵称模式（甲）

- 无 token 时：`browser.ts:169-200 ensureDesktopClientToken` → `:175-178` → `bootstrapDesktopClientTokenWithLock`（:138-149，跨窗 lease 见 `desktop-login.ts:56-133`，DSK-07）→ `bootstrapDesktopClientToken`（:111-134）。
- 请求体是**硬编码**的：`nickname: "WorkHub Desktop"`, `device_name: "WorkHub Desktop"`, `platform: "desktop"`（`browser.ts:113-117`）。工作台窗同款硬编码（`workbench/boot.ts:102-106`）。
- 服务端 `POST /api/auth/desktop-bootstrap`（`apps/api/src/routes/auth.ts:402`）昵称分支 :439-478：`validateNickname` → `getOrCreateActiveByNickname`（:441）→ 若命中的是管理员账号则要 `admin_secret` 且带限流（:442-457）→ `ensureDefaultWorkspaceMembership`（:459，实现 :264-323，只建**工作区成员**，不建项目）→ `makeClientToken` + `createClientDevice` → 201 返回 `{identity, device, client_token}`。
- `getOrCreateActiveByNickname`（`packages/db/src/repositories/users.ts:158-185`）**按昵称查已有 active 用户，命中即复用**。
  → **全团队每台 Mac 首启都以同一个昵称 `WorkHub Desktop` 落到同一个 user 行**。甲和他同事装同一个 `.app`，在服务器上是同一个人。首启**从来不问「你是谁」**——问昵称的那张屏（`desktop-rebind.ts:67-95`）只在显式登出态才渲（`browser.ts:283-286`）。
- 令牌落地：明文写 localStorage `workhub_client_token`（`desktop-client-token.ts:14,28-30`），随后推给 Rust 壳层供 SSE 鉴权（`browser.ts:79-90` → `main.rs:495-522 set_client_token`，含身份代际递增）。

### 3.2 密码/hybrid 模式（乙）

- 设计链路：`desktop-bootstrap` 在密码模式下、无会话时回 **404**（`auth.ts:402-407` 的模式分支 + :419-421 的 `if (!user) 404`）→ `isPasswordModeBootstrapError`（`desktop-login.ts:146-148`）→ gate `needs-credentials` → 渲凭据登录门（`browser.ts:277-280` → `desktop-login.ts:243-297`；工作台同款 `workbench/boot.ts:274-282`）→ 表单提交走 `runDesktopCredentialLogin`（`desktop-login.ts:155-176`）：`POST /api/auth/login` 建会话 → 再打 `desktop-bootstrap` 用会话换 `client_token`（服务端 :407-437 的 exchange 分支）→ 落盘 + 清登出标记 → reload。
- **但乙走不到这一步**：api base 仍是 `127.0.0.1:8787`（没有任何入口让他先改地址），bootstrap 拿到的是**网络错误**而不是 404 → `browser.ts:124-133` 的 catch 判不出密码模式 → 返回 `"unavailable"` → gate `"offline"` → `bootSpotlight` 对 `"offline"` **没有任何分支**（:277 只判 `needs-credentials`、:283 只判 `logged-out`）→ 继续挂载空的 Spotlight。凭据登录门永远不出现。
- **桌面端没有注册、也没有「接受邀请」屏**：`desktop-login.ts` 只有邮箱+密码两个字段（:229-234）；全仓 grep 显示桌面只有「**生成**邀请」（管理员在工作台 rail，`workbench/rail.ts:557-590`），接受邀请的落地页只在 web（`apps/web/src/browser.ts:6404` 的 `/invite` 路由 → 服务端 `auth.ts:826`）。乙作为受邀用户**必须先在浏览器里接受邀请、设昵称和密码**，才可能回到桌面端登录。web 的登录屏还有注册页签（`apps/web/src/auth-screen-mode.ts:44,53-61` 的 register 分支），桌面没有。

### 3.3 登出 / 重绑 / 令牌失效

- 登出入口在 Spotlight 设置视图（`spotlight/views/settings.ts:559-561` 的按钮，:1326-1360 的副作用）：①服务端 `POST /api/auth/logout` ②`set_client_token("")` 清壳层（`main.rs:496-508`）③清 localStorage 令牌 + 写 `workhub_desktop_logged_out=1` ④广播 `workhub-logged-out` ⑤reload。失败有可见面板 + 重试 + 「仍要本地退出」（:882-907）。顺序不可吞错（R20 SEC P1-01，:820-830 注释）。
- 登出后：昵称模式渲重绑屏（`browser.ts:283-286` → `desktop-rebind.ts:99-151`），密码模式按 `workhub_auth_mode` 提示渲凭据门（`browser.ts:170-174`，提示键 `desktop-login.ts:22-40`）。
- 令牌陈旧/被吊销：`browser.ts:179-192` 每次 boot 都探活一次 `client.me()`，命中 `not_identified`/`invalid_client_token`（`auth-recovery.ts:3-5`）就清掉重铸。工作台同款（`workbench/boot.ts:78-89`）。**这一条是好的**：不需要用户手清 localStorage。
- 其它窗口跟随：工作台切到「已登出」整窗态（`workbench/shell.ts:192-206`），桌宠换成「已登出」卡（`pet-surface.ts:851-869`）。

## 5. 深链 / 单实例 / 托盘 / 通知在首启链路上的表现

- **深链 scheme**：`workhub`、`yqgl`（`tauri.conf.json:74-79`）。运行时 `register_all()` **只在 Windows/Linux 执行**（`main.rs:1629-1637` 的 `#[cfg(any(windows, target_os = "linux"))]`）；macOS 靠打包器把 plugin 配置注入 `CFBundleURLTypes`——而手写的 `client-tauri/src-tauri/Info.plist` 只有 `LSRequiresCarbon`，没有 URL types 段。**需要在真实 `.app` 上核实一次**（我只能证明手写 plist 里没有，无法在只读侦察中证明打包器是否补上）。
- 冷启动 URL 走 `get_current()`（`main.rs:1640-1655`，畸形链接只打日志不阻断启动）；运行期走 `on_open_url`（:1657-1663）。
- **单实例**：插件已注册（`main.rs:1914-1918`）；第二次启动聚焦 main 并重放 argv 里的深链（`single_instance.rs:21-50`）。
- **深链丢事件兜底**（MRG-23）：壳层按目标窗 label 暂存最后一条计划，webview 挂载后取回（`browser.ts:358-365`、`workbench/boot.ts:192-207`，命令 `take_pending_deep_link` 在 `main.rs:1757`）。登出态不消费 stash（MRG-22，`workbench/boot.ts:241-251,299-303`）。
- **托盘**：启动即装，8 项菜单（`tray.rs:13-26`，装载 `main.rs:1966`）。带 Dock/托盘角标（`browser.ts:94-105 set_shell_badge` → `main.rs:562`）。
- **通知**：权限在**第一条通知要发时**才请求（`notify.rs:143-155`），不是首启就弹。
- **关键联动**：托盘角标、系统通知、Cuu 上线全部依赖 Rust SSE worker 连上 `config.server_url`。甲/乙的 server_url 都是默认 `127.0.0.1:8787` 且无法在界面里改 → **首启后托盘角标恒 0、系统通知恒不响、桌宠恒「重连中」**，即使 webview 侧的地址被改对了也一样。

## 6. 断点 / 困惑点 / 缺失（按严重度）

### P0

**E-01 · 打包后 CSP `connect-src` 拦死一切非回环后端**
`tauri.conf.json:16` 只放行 `'self' ipc: 127.0.0.1:* localhost:*`。甲的 `192.168.1.10:8787` 和乙的 `https://workhub.example.com` 全部被浏览器层拒绝，改地址也没用。README 三步走部署出来的服务器（`README.md:61-63` 的 `http://<这台机器的IP>:8787`）在桌面端 100% 不可达。dev 态被 Vite 代理掩盖（`vite.config.ts:11-14`），只在 `.app` 里发作。

**E-02 · 「连不上后端」不渲离线卡，而是一个空壳搜索盒（服务器地址入口因此实际不可达）**
`ensureDesktopClientToken` 把所有网络失败吞成 `"unavailable"`（`browser.ts:124-133`）→ 返回 gate `"offline"`（:195-199）；`bootSpotlight` 只处理 `needs-credentials`（:277）和 `logged-out`（:283），**没有 `"offline"` 分支**，继续 `client.me().catch(() => null)`（:289）、`mountSpotlight`（:318，纯同步 DOM，不会抛）。离线卡只在 `catch` 里渲（:395-397），而这条路径根本不抛异常。
后果：用户看到一个「正常」的搜索条，输入什么都没结果、没有一句错误、**没有任何入口能走到那个唯一的「服务器地址」输入框**。工作台窗更彻底——`workbench/boot.ts` 连离线卡都没有（gate `"offline"` 直接落到 :290 `mountWorkbenchShell`），只有未捕获异常才渲致命错误面板（:314-321）。

**E-03 · 首启从不问「你是谁」，全团队塌成同一个账号（昵称模式）**
`browser.ts:113-117` / `workbench/boot.ts:102-106` 硬编码 `nickname: "WorkHub Desktop"`；服务端按昵称复用同一 user 行（`users.ts:158-162`）。甲和同事装同一个包 = 服务器上同一个人，消息、审批、个人记忆全混。问昵称的 UI 存在但只在登出后可达（`browser.ts:283-286`）。

**E-04 · 密码/hybrid 用户的登录门永远不出现**
乙的 bootstrap 因为地址错而报网络错误（不是 404），`isPasswordModeBootstrapError` 判不中（`desktop-login.ts:146-148`），gate 落 `"offline"` 而非 `"needs-credentials"`。凭据表单（`desktop-login.ts:202-239`）在乙的机器上是死代码。

### P1

**E-05 · 桌面端没有注册屏、没有「接受邀请」屏**
`desktop-login.ts:229-234` 只有邮箱+密码。接受邀请只在 web（`apps/web/src/browser.ts:6404`；服务端 `auth.ts:826`）。乙必须先离开桌面端、开浏览器、接受邀请设密码，才能回来登录——而 README/DEPLOY 里根本没说桌面客户端这回事。

**E-06 · Rust 壳层的 `server_url` 与 webview 的 api base 是两份，且壳层那份没有界面入口**

## 7. 设计提案（最小完整）

### 7.1 目标三屏

```
[连接服务器]  →  [模式感知的登录/注册]  →  [落地页]
```

**屏 1 · 连接服务器**（新，取代当前「什么都不说的空搜索盒」）

- 触发条件：`workhub_api_base` 未设置，或对当前 base 的连通性探测失败（把 `bootSpotlight` 里缺失的 `gate === "offline"` 分支补上，`browser.ts:277-286` 同层；工作台 `workbench/boot.ts:274` 同层）。
- 内容：地址输入（预填默认值）+ 「测试连接」+ 「记住这台服务器」+ 结果卡片（服务器名 / 版本 / 认证模式 / AI 是否配置）+ 高级详情折叠（原始错误）。
- 校验：复用 `normalizeDesktopApiBase`（`desktop-api-base.ts:18-38`），一字不改。
- 探测端点：`GET /api/health`。**需要扩契约**——当前只返回 `{ok, service, env, runtime, port, ai_provider_configured}`（`apps/api/src/app.ts:221-230`），缺 `auth_mode`、`version`、`instance_name`。补上这三个字段后：
  - 「测试连接」一次拿到全部展示信息；
  - 登录屏不再需要 web 那套「拿 identify 的 404 当探针」的取巧（`apps/web/src/auth-screen-mode.ts:5-38` 自陈是权衡之举），桌面直接读 `auth_mode`；
  - `desktop-bootstrap` 的 404 判定（`desktop-login.ts:146-148`）保留作降级路径（连老服务端也能工作）。

**屏 2 · 模式感知的登录/注册**

- `auth_mode === "nickname"`：渲昵称屏——**直接复用 `desktop-rebind.ts:67-95` 那张屏**（它已经是「输入昵称 → desktop-bootstrap → 落 token」的完整流程，`runDesktopRebind` 在 :34-56），把标题从「已登出」改成首启文案即可。同时**删掉 `browser.ts:113-117` / `workbench/boot.ts:102-106` 的硬编码昵称**（E-03 的根治）。
- `auth_mode === "password" | "hybrid"`：渲现有凭据门（`desktop-login.ts:243-297`）+ 新增两个页签：
  - 「注册」：`POST /api/auth/register`（`auth.ts:481`，api-client 已有 `register`，`packages/api-client/src/client.ts:488-497`）；文案照 web 的 `describeAuthScreenError`（`apps/web/src/auth-screen-mode.ts:44-71`）。
  - 「我有邀请令牌」：`POST /api/auth/invites/accept`（`auth.ts:826`）；表单 = 令牌 + 昵称 + 密码，成功后接既有的 exchange（`desktop-login.ts:164-169`）。

### 7.2 CSP 策略取舍与推荐

| 方案 | 做法 | 代价 | 残余风险 |
|---|---|---|---|
| **a** | `connect-src` 放开 `http: https: ws: wss:`（保留 `script-src 'self'` / `object-src 'none'`），把「连哪个主机」的判断完全交给应用层（`normalizeDesktopApiBase` + 用户显式确认 + 单 origin 钉死） | 改一行 conf | 若 webview 里跑起攻击者 JS，令牌可外发到任意主机（DSK-05 的原始担忧） |
| **b** | 用户确认过的 origin 写进壳层配置，所有 API/SSE 改由 Rust 侧 reqwest 代理，CSP 维持只放行 `ipc:` | 全部 fetch/SSE/网盘下载/头像 blob 都要改走 IPC 通道；流式语义、CORS、Range 都要重验 | 最小——令牌可完全不进 webview |
| **c** | 保持现状 + 只把「打包后连远端」宣布为不支持，产品退回 web | 桌面端作为产品核心的定位作废 | — |

**推荐：a 现在做，b 作为终局；不选 c。**

理由：
1. **Tauri v2 的 CSP 是打包期静态串**，写在 `tauri.conf.json:16`，没有「按用户配置动态生成 origin 白名单」这条路。方案 b 的白名单只能靠 Rust 代理来强制执行，而不是靠 CSP——所以 b 的成本是「重写整个数据层」，不是「改配置」。`.agents/notes/proposed/2026-08-20-desktop-client-token-shell-storage.md` 的 "Alternatives considered" 已经把这笔账算过：「彻底，但工作量大——所有 fetch/SSE 都要改走代理通道」。
2. **CSP 现在挡的不是入口，是出口**。入口（`script-src 'self'`、`object-src 'none'`、无 `unsafe-eval`）不变。而令牌本来就明文躺在 localStorage（`desktop-client-token.ts:1-9` 自陈），能跑 JS 的攻击者即使不发网络请求，也可以经 `workhub://` 深链、剪贴板、或把令牌编码进一个「合法」的回环请求路径渗出——`connect-src` 只是提高了一点门槛，不是边界。
3. **代价对比悬殊**：为一个残余风险控制，换掉产品的核心使用场景（自托管服务器不在本机）——这笔账不划算。SA-01 把它列为「高」也是这个意思。

**方案 a 的补偿控制（必须同批落地，缺一不可）**：
- **C1 单 origin 钉死**：api-client 层加一道断言——所有请求的目标 origin 必须等于当前配置的 api base origin，否则直接拒。这有现成先例：DSK-08 就是给 run 流 URL 加同源校验（台账 `reports/审查台账-2026-08-19.md:55`）。
- **C2 地址只能由人手敲**：连接屏的地址永远来自用户键盘输入，**绝不**从深链、剪贴板、`window.name`、或任何响应体里自动采纳。改地址必须走「测试连接 → 看到服务器信息 → 显式确认」三步。
- **C3 换服务器即清身份**：地址一变，立刻清 `workhub_client_token` + `set_client_token("")`（复用 `settings.ts:1331-1340` 的 `clearLocalIdentity`），杜绝把 A 服务器的令牌发给 B。
- **C4 把令牌迁到壳层**（= `.agents/notes/proposed/2026-08-20-...` 那份提案，状态 proposed）。**这才是 DSK-05/DSK-06 的真修法**；它落地后，`connect-src` 松紧对令牌外泄的影响趋近于零。建议把这份 Note 从 proposed 提到「本轮排期」，但不阻塞 a。

**对 DSK-05 风险的净影响**：短期**上升**（从「难以外泄」变成「可外泄」），但基线本来就是「同进程 JS 可读明文令牌」；C1+C2+C3 把「被诱导连到攻击者服务器」这条更现实的攻击面按住了，C4 落地后净风险**低于今天**。台账里 DSK-05 的原始描述是「`connect-src` 全开 + `workhub_api_base` 无校验」两件事（`reports/审查台账-2026-08-19.md:52`）——**校验那一半保留且加强，只放开 CSP 那一半**，不是回退到修复前。

### 7.3 三窗共享与热更新

- **单一真相**：localStorage `workhub_api_base` 仍是 webview 侧唯一真相（三窗同源天然共享）。
- **壳层跟随**：新增 Tauri 命令 `set_server_url(url)`：
  1. Rust 侧用与 `normalizeDesktopApiBase` 同口径的规则再校验一次（`config.rs:63-65` 的 `normalize_server_url` 目前只 trim + 去尾斜杠，要补 scheme 校验）；
  2. 落盘 `workhub-shell-config.json`（路径已有 `main.rs:1849-1853`）；
  3. 重建 SSE worker 订阅（`sse_worker.rs:154-158` 的 plan 目前只在 setup 建一次，要改成可重启/可换 base——最小做法是把 `WorkHubShellConfig` 放进 `.manage()` 的 `Mutex` 并让 worker 每次重连前重读，与既有的 `ShellClientToken` 代际机制同款，`sse_worker.rs:30-85`）；
  4. `app.emit("workhub-server-changed", {url})`。
- **跨窗热更新**：三窗订阅 `workhub-server-changed` 后自行 reload——**复用既有的 `workhub-logged-out` 广播模式**（发送 `settings.ts:1343-1349`，订阅 `workbench/boot.ts:217-228`、`pet-surface.ts:1737`），不新造协议。
- **顺序**：清令牌（C3）→ 写 localStorage → `set_server_url` → 广播 → 各窗 reload → 重新走屏 2。
