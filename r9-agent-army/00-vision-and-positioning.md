# R9 · 愿景与定位:每个人背后,一支巨型 agent 军团

> 状态:规划中(2026-06-23 起草)· 上游:R8 巨型重构(进行中)· 灵感来源:Matrix agentic-runtime 概念稿
> 一句话:把 WorkHub 从"AI 当默认劳动力的协作中台",推进到"**给每一个人配一支能自己拆解、执行、自证的 agent 军团**"。

---

## 0. 这一程要改的那个假设

WorkHub README 里立过一个颠倒:几乎所有协作工具都默认"活儿主要靠人干,AI 是助手",而 WorkHub 把它倒过来——**AI 是第一个动手的,人退回去做判断**。R0–R8 把这个倒转的**地基**修好了:提议→审批→合并的业务版 GitHub、AgentRun 引擎、真 LLM 端到端跑通、记忆/技能/成本的雏形、桌面 Cuu 与 web 的项目优先重构。

R9 要改的是**下一层假设**:

> 今天的 AI 还是"一个 agent 接一个任务"。
> R9 要让它变成"**一个意图,落到一支会自己分工的 agent 军团**"。

不是把单个 agent 做得更强,而是让**编排本身**成为产品:任务进来,自动拆解成子任务,派给各自带独立记忆与技能的子 agent,并行推进,每一步都返回可验证的证明,最后按目标复盘、回灌记忆与技能,下次更强。

---

## 1. 定位:不是"0 人公司",是"每个人 +1 支军团"

灵感稿 Matrix 打的旗号是"0 人公司 / 从第一天就赚钱 / agent 自动办实体、银行卡、域名、邮箱"。**我们明确不采用这个 framing**,原因有二:

1. **不真实、且危险**。让 agent 自动注册公司、办银行卡、接受 ToS、处理付款,恰恰是 KYC / 验证码 / 法律责任卡死的高风险动作,也是我们安全底线里"必须人来做"的那一类。把它写进愿景,等于把产品建在一个做不到、也不该做的承诺上。
2. **和 WorkHub 的底线冲突**。WorkHub 的北极星是**自主率**,但护栏写得死死的:"自主率再高,也绝不拿信任去换"。"0 人"在叙事上就是拿"无人值守"去换信任。

我们的 framing 是用户自己定的、也更诚实的那句:

> **不是一家没有人的公司,而是每一个人的背后,都站着一支巨型 agent 军团。**

区别不是文字游戏,是产品形态的分叉:

| | 0 人公司(不采用) | 每人一支军团(R9) |
|---|---|---|
| 人的位置 | 被移除 | 在中心,当指挥官 / 审批者 |
| 自治边界 | 无人值守,直到出事 | 自治到"该敲门的那一刻"为止 |
| 高风险动作 | agent 自己办 | 永远升级给人(法务/财务/身份) |
| 失败叙事 | happy-path,藏起困难状态 | 困难状态(卡死/升级/打回)是一等公民 |
| 商业承诺 | "替代你" | "放大你"——一个人指挥很多 agent 的杠杆 |

这条线接得上 WorkHub 已有的哲学:孔子"君子不器"——把工具性劳动还给工具,人去做判断、负责、拍板这些"不器"的事。**军团越大,越要把"该人来拍的板"清清楚楚交还给人。**

---

## 2. 从灵感稿提炼的 6 条设计哲学(我们采纳的部分)

Matrix 概念稿值得借鉴的是它的**架构直觉**,不是它的营销。提炼成 6 条,作为 R9 的设计准则:

1. **结果 / 证明驱动**(没有证明,就不算完成)。完成的定义不是 agent 说"做完了",而是返回可验证的证据。— 这条和 WorkHub 的"每处改动都留得下快照、走提议→审批"是同一个灵魂,R9 要把它贯穿到每个子 agent。
2. **组织即运行时**(Org-as-runtime)。意图 → CEO Office(设目标/政策/节奏)→ OKR(优先级记忆)→ 部门(Lead + Worker 并行)→ 结果 → 复盘回灌。**层级结构本身就是调度器**。
3. **每个 agent 是 operator,不是 assistant**。各自有工具、文件、记忆,在真实工作的地方工作。
4. **持久记忆是一等公民**。工作会记住自己;记忆与技能被收割下来下次复用——这是复利的来源。
5. **长周期主动执行**。定义一个 Objective,系统跑几天/几周,而不是一轮就停。
6. **异构 agent 的元编排**。Matrix 自己写明"编排 Neo、Claude Code、Codex 等 agent"——它是骑在多种 runtime 之上的调度层,不是单个模型。R9 同构:WorkHub 编排自己的 AgentRun + 可插拔的外部 agent。

## 3. 用户拍板的设计决策(2026-06-23)

本程序的形态由用户明确定下,记录在此作为后续所有文档的约束:

- **四件核心资产**:**任务(task)、子 agent(sub-agent)、技能库(skill library)、记忆库(memory library)**。
- **meta-planner**:负责"拆解的泛化"——把任意人类任务拆成子任务/子 agent,而不是写死四个固定部门。这是整套能不能泛化的胜负手。
- **OKR System**:要上。作为"优先级记忆",承接 Matrix 里 CEO Office ↔ OKR 那条回路。
- **LLM-judge**:作为**主 agent 的一部分**内置,而不是独立服务——主 agent 自带"按目标/key result 验收"的能力。
- **预算(budget)**:按工程建议做成**一等的、可见的、有硬上限的资源**(详见 04 可行性与风险)。
- **定位**:每个人背后一支巨型 agent 军团(见 §1)。

## 4. 这一程的成败,不在"agent 跑不跑"

R5.10 已用真 DeepSeek key 端到端验证过 AgentRun——"agent 能不能跑"这关早过了。R9 的真正难点是**编排层的四件难事**(详见 01 架构 / 02 记忆 / 04 可行性):

1. **拆解的泛化** —— 固定部门不泛化,需要 meta-planner 或领域模板库。
2. **记忆的三层架构 + 冲突归并** —— 私有(每子 agent)/ 共享治理(OKR)/ 收割技能,三层之间的读写边界与冲突解决必须前置设计,否则记忆会腐烂、互相打架。WorkHub 在 P-COLLAB 合并上已有可复用的原语。
3. **证明的定义** —— 客观处(代码/CI/指标)用硬门,模糊处(创意/营销)用 LLM-judge + 对抗式验证,绝不让 agent 自证。
4. **人类逃生舱 + 成本天花板** —— 决策信箱与预算硬上限不是可选项,是让长周期自治安全的阀门。注意现存"escalated 死状态"坑要先修。
