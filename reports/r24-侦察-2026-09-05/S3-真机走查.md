## 三、易用性发现

### 阻断（新用户第一天就走不下去）

**B-01 全新安装 + 没有后端 = 一个看起来一切正常的空壳，且无处填服务器地址**
截图 `41-fresh-no-backend-main.png` / `42-fresh-no-backend-expanded.png`。
后端完全没起时，桌面端照常显示 idle 搜索条和 18 个能力，点进去才逐个静默失败。
`desktop-offline-card.ts` 里那张带「服务器地址」输入框的离线卡**在这条路径上永远不会渲染**：
- `apps/desktop-webview/src/browser.ts:199` 在拿不到 token 时返回 gate `"offline"`；
- `apps/desktop-webview/src/browser.ts:277-286` 只处理了 `needs-credentials` 和 `logged-out`，
  **没有 `offline` 分支**，直接往下挂载完整 Spotlight；
- `apps/desktop-webview/src/browser.ts:396` 的 `renderDesktopOfflineCard` 只在整个 try 块抛异常时才跑，
  而 `ensureDesktopClientToken` 吞掉网络错误、`client.me()` 是 `.catch(() => null)`、角标刷新自带 try/catch
  ——**没有任何东西会抛出来**。
连带后果：设置页也没有服务器地址项（见 `28/29/30-settings*.png`），所以整个产品**没有任何 UI 能改后端地址**。

**B-02 打包后的桌面端只能连本机回环，连 LAN 地址被 CSP 静默拦死**
截图 `43-lan-csp-blocked-main.png` / `44-lan-csp-blocked-pet.png`。
实测（对照实验，同一台探针服务器 0.0.0.0:8799，curl 两个地址都 200）：
- 对照组 `workhub_api_base = http://127.0.0.1:8799` → 探针立刻收到
  `OPTIONS /api/auth/desktop-bootstrap`、`GET /api/auth/me`、`GET /api/pages/attention`，
  Origin 均为 `tauri://localhost`；
- 实验组 `workhub_api_base = http://192.168.51.155:8799`（本机 LAN IP）→ 探针 **0 条请求**。
根因是静态 CSP：`client-tauri/src-tauri/tauri.conf.json`（`app.security.csp`）的 connect-src 只放行
`'self' ipc: http://ipc.localhost http://127.0.0.1:* http://localhost:* ws://127.0.0.1:* ws://localhost:*`。
对一个「局域网团队部署、服务器跑在别人机器上」的产品，这等于桌面端不可用；且失败**没有任何报错**，
主窗一片正常，只有桌宠含糊地说「Connection is unstable」。
（另：`WORKHUB_SERVER_URL` 环境变量只喂 Rust 壳的 SSE worker
`client-tauri/src-tauri/src/config.rs:5`，webview 的 API base 只读 localStorage
`apps/desktop-webview/src/browser.ts:68-70`，两者根本不是同一个配置——配置面分裂。）

**B-03 首页主 CTA「New task / Ask AI」必然失败，且提示是错的**
截图 `10/11/12/13-*.png`、`51-newtask-with-project.png`。
两段连着的失败：
1. 全新服务器没有任何项目 → `POST /api/sessions` 返回 **404 `project_not_found`**
   「还没有可用项目，无法创建任务。」
2. 建好项目之后、没有 LLM key → `POST /api/sessions` 返回 **503 `clarification_llm_unavailable`**
   「AI material analysis is not configured, so WorkHub cannot generate a real clarification question.」
两次桌面端都只弹一条 3.2 秒的 toast **"Couldn't start — retry" / 「开场失败，请重试」**
（`apps/desktop-webview/src/spotlight/views/intake.ts:179`），把服务端唯一可行动的信息整个丢掉，
还劝用户「重试」——而重试永远不可能成功。
同时 intake 面板上**没有** AI 未配置横幅（工作台聊天区却有，见 `26-*.png`），
文案还在承诺「Cuu clarifies a few points, then works and brings it back for review」。

### 严重

**S-01 同一个 app 三个窗口三种语言 / 状态，且服务端会把用户语言改掉**
截图 `17-workbench-first-open.png`（工作台中文）对 `15-launcher-list.png`（主窗英文），
`36-offline-workbench.png`（一张图里同时看到工作台中文 + 主窗英文 + 桌宠英文）。
三处独立成因：
- 服务端 `users.preferred_locale` 列默认 `'zh-CN'`（迁移 schema），`/api/auth/me` 回 `locale:"zh-CN"`；
  `packages/web-runtime/src/locale.ts:66 applyIdentityLocale` 用它**覆盖**浏览器/系统语言，
  并且 `persistBrowserLocale` 把它写回 localStorage。工作台 `apps/desktop-webview/src/workbench/boot.ts:259`
  与主窗 `apps/desktop-webview/src/browser.ts:290` 都会走这条。
  **实测已复现污染**：首次运行主窗是英文，开过工作台并重启后主窗变成中文
  （`38-coldstart-no-backend-spotlight.png`、`46/47-settings-*-zh.png`、`50-after-relogin.png`）。
- Rust 壳的 locale 默认写死中文且从不读系统语言：
  `client-tauri/src-tauri/src/config.rs:22`（`lan_default()` 用 `WorkHubLocale::default()`）+
  `client-tauri/src-tauri/src/locale.rs:4`（`DEFAULT_WORKHUB_LOCALE = ZhCn`）。
  实测托盘菜单全中文：`打开 WorkHub / 隐藏主窗 / 显示-隐藏 Cuu / 恢复 Cuu 交互 / 打开收件箱 / 设置 / 打开工作台 / 退出 WorkHub`
  （`client-tauri/src-tauri/src/tray.rs:56 default_tray_menu_items()` 用的就是这个默认）。
- 窗口标题写死中文：`client-tauri/src-tauri/tauri.conf.json` 里 workbench 窗 `"title": "WorkHub 工作台"`。

**S-02 后端已死，工作台还在说「已连接」**

**S-03 深链 `workhub://` 全部失效（热态）**
截图 `31-deeplink-notifications.png`。
`open workhub://open/notifications`、`workhub://open/settings`、`workhub://open/approvals`
三条都只是把 app 拉到前台并把聚焦盒**复位成 idle 条**，没有打开对应能力。
Rust 侧解析映射是对的（`client-tauri/src-tauri/src/deep_link.rs:180` → `/notifications`），
webview 侧路由→能力表也在（`apps/desktop-webview/src/spotlight/state.ts:99`），
但实际落到了 `apps/desktop-webview/src/spotlight-shell-navigation.ts:32` 的 `spotlight.reset()` 分支——
即 `navigate` 事件的 payload 没被 `parseDesktopShellNavigatePayload` 认下来，或事件根本没到主窗。
托盘的「打开收件箱 / 设置」走的是同一条 `execute_window_control` → `app.emit("navigate", route)`
（`client-tauri/src-tauri/src/main.rs:898`），因此很可能同样失效。

**S-04 首启并发 bootstrap 打出一个未捕获 500**
API 日志（首启那一刻，两个窗口同时打 `POST /api/auth/desktop-bootstrap`）：
```
07:19:16.619 ERROR unhandled_error path=/api/auth/desktop-bootstrap
  error=Failed query: insert into "workspace_memberships" ...
  at packages/db/src/repositories/memberships.ts:176
07:19:16.619 POST /api/auth/desktop-bootstrap status=500
07:19:16.620 POST /api/auth/desktop-bootstrap status=201
```
`apps/api/src/routes/auth.ts:295` 的 `isUniqueViolation` 判定用 `error.code === "23505"`
（`apps/api/src/routes/auth.ts:70`），但 drizzle-orm 0.45.2 把 pg 错误包成
`Error: Failed query: …` 并把原始错误挂在 `.cause` 上——**顶层没有 `.code`，这个幂等守卫是死代码**，
唯一冲突直接冒泡成 500。
同时说明 `apps/desktop-webview/src/desktop-login.ts:52` 的跨窗 localStorage lease（DSK-07）
挡不住主窗/桌宠两个 WKWebView 进程的同刻竞态。用户侧这次没炸（另一条 201 成了），但这是真 500。

## 四、未能验证的项与原因

1. **原生系统通知的实际弹出与点击跳转** — 没有 LLM key、没有第二个人，整个走查期间服务端没产生任何
   通知事件（`GET /api/notifications` 恒为 0）。造通知需要直接写库或用真 key 跑 AgentRun，
   超出「不用真实 LLM key」的约束。
2. **webview devtools / 前端 console 报错** — release 打包的 Tauri 未开 devtools，
   无法打开检查器。用 API 日志 + 探针服务器做了等价的网络层观察。
3. **托盘菜单项的实际点击效果**（打开收件箱/设置/打开工作台）— 只通过辅助功能读到了菜单项文本并
   成功执行了「退出 WorkHub」；其余项因与 S-03 深链同走 `emit("navigate")` 通道，推断同样失效，
   但未逐项点击验证。
4. **多人协同**（两台设备/两个用户互相看到对方）— 单机走查，只建了 `WorkHub Desktop` 和 `Alex Chen`
   两个账号但没有并行客户端。
5. **真实 LAN 上另一台机器连本机服务器** — 用本机 LAN IP + 探针服务器做了等价实验（结论确定：
   CSP 层就拦死了，与对端是否可达无关）。
6. **`WORKHUB_SERVER_URL` 环境变量对 Rust SSE worker 的实际效果** — 只做了代码确认
   （它不影响 webview 的 API base），没有跑通「壳层连 A、webview 连 B」的分裂实验。
7. **Retina 以外的屏幕 / 小屏笔记本** — 设置页展开高 855pt，本机 1117pt 屏放得下；
   13 寸 MacBook（可用高度约 800pt）是否溢出未验证。
