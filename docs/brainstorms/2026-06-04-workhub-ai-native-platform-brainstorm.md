# WorkHub —— AI-native 工作中台(「业务版 GitHub」)

## What We're Building / 我们要造什么

把现有的「需求管理大师」进化成一个**全新项目 WorkHub**(新建 GitHub 仓库):面向业务 / 非开发者的协作中台,核心是一条原则——**AI 跑流程,人来拍板**(Agent 提议 → 人确认),并把它推到极致,成为默认而非个别环节。

最激进、也是 WorkHub 的灵魂——**AI 一人两顶帽子,受阻即换帽**:

- **默认:AI 是「工人」**,直接产出交付物(写文档 / 做分析 / 出方案 / 写代码)。
- **触发器一响,AI 秒变「项目经理」**,不再硬扛,转而组织人来完成(派活、排期、提醒、盯进度、再审)。
- 触发器 = ① 不合格 ② 用户不满意 ③ 用户明确不让 AI 干。

人类从"主力"退位为**异常处理器 + 审批者**。外壳是一套**去 git 黑话的 GitHub 模型**:协作者各干各的"分支",AI 拟好改动 → 负责人审 → 合并到 main;但用户看到的不是 merge / 分支 / 冲突,而是「AI 拟好了,确认?」。入口是**桌面宠物**(替代右下角弹窗)+ web,Agent 几乎能操作所有功能;辅以双向同步、README = 需求规格展示页。

## Why This Approach / 为什么是这个路线

- 现有产品的 deliver → 负责人「通过 / 打回」循环,本质已是 GitHub 的「PR 审查 → 合并」。**脊梁骨已有**,WorkHub 是命名 + 延展,不是从零。
- 「AI 工人 ⇄ AI 项目经理」两模式,优雅化解了"AI 做交付物 vs AI 做编排"的分叉——它们是同一 Agent 的两种状态,**切换条件 = 升级条件**。
- 三个升级触发器几乎都已有代码支撑(见下),从想法到落地的距离很短。
- opencode 源码研究证实:**这套架构有成熟先例**,且它的 permission 模型几乎就是 WorkHub 升级层的现成答案(见「技术参照」)。

## Key Decisions / 关键决策

- **心脏 = AI-native「Agent 提议 → 人确认」**,且为默认。(用户原话:"纯正 AI 驱动的 AI NATIVE 中台")
- **AI 默认做交付物本身**(L2 执行),不是只做编排;受阻才转编排(L1)。
- **升级判定 = 置信度 / 风险分级**:高置信 → 直接合并 main;中等 → 人工抽检;低置信 / 高风险 → 直接转项目经理模式找人。(避免"自评太松埋雷"与"自评太严沦为空话"两极)
- **三个升级触发器**:① 不合格 ② 用户不满意 ③ 用户明确不让 AI 干。
- **智能派活为旗舰样板**:Agent 据「技能自述 + 自我介绍 + 既往协作画像」提议 负责人 + 协作人,人确认 / 调整。
- **全都要,但分层装**:L0 身份档案 / L1 AI 项目经理编排 / L2 AI 劳动力执行 / L3 协作(分支-提议-合并、双向同步、README=规格)/ L4 入口(桌宠 + web)。
- **新建独立仓库**;理念上是把现有零件串成自治闭环,而非推倒重来(重写 vs 迁移待定,见开放问题)。

## 技术参照:opencode 给的现成答案

研究了 `sst/opencode`(TS / Bun / Effect / Vercel AI SDK / **headless HTTP server + OpenAPI + SSE**)。直接可借鉴(详见 `D:/02_代码与开发/_workhub_research/opencode`):

1. **审批 = 阻塞原语**:任何工具在"该决策的那一刻"主动 `ask` 人;策略是分层、通配、**默认就问(ask-by-default)**的 allow/deny/ask;"永远允许"会沉淀成自动规则。→ **这就是 WorkHub 的升级层 + 置信度分级落地方式。**
2. **打回带理由会回灌给模型**(reject-with-feedback):人说"不,改成 X" → 变成下一步的工具结果,AI 自我纠偏而非停摆。→ 完美对应「用户不满意 → 打回」。
3. **Doom-loop 检测 + step 预算耗尽 → 强制结构化总结**:连续 N 次相同调用判定"卡住"自动升级;预算用尽则产出"做了什么 / 还剩什么"的交接件。→ 把「做砸了 / 做不了才找人」变成两个具体可触发的信号。
4. **headless agent 守护进程 + 类型化 SDK + SSE 事件流**:CLI / 桌面 / web 都只是瘦客户端。→ 直接满足"桌宠 + web 共用一个 Agent",权限询问 / 进度 / 结果都只是流上的事件。
5. **Agent = 权限画像 + 系统提示 + 模型**,内置 plan(只读研究)/ explore 模式,子 agent 最小权限继承。→ WorkHub「工人 / 项目经理」两模式与自治分级的现成骨架。
6. **provider 抽象**:DeepSeek-via-Anthropic 兼容端点可直接作为一个 provider 接入,系统其余部分保持模型无关。

## Open Questions / 开放问题(进入 planning 前需收敛)

1. **新仓库策略**:全新重写,还是把现有 FastAPI+SQLite+Tauri 地基迁入新仓再演进?(影响巨大,且不依赖更多研究——可现在定)
2. **技术底座**:opencode 证明了"headless agent daemon + OpenAPI + SSE + 类型化客户端"是对的架构。语言(Python 续用 vs 转 TS)是次要选择;**真正要逃离的是现有 SQLite「必须单 worker」的天花板**——多 Agent + 多用户并发下它撑不住。
3. **部署形态**:沿用今天的"局域网 + 免登录 + 设备令牌",还是走云端 / 多租户?("在 GitHub 建库" + web + 跨协作者分支 似乎暗示更开放——可现在定)
4. **置信度分级怎么标定**:置信度从哪来(AI 自报?历史命中率校准?)、各档阈值、"高风险任务"如何定义。(opencode 的 doom-loop / 预算耗尽可作为基线信号)
5. **冷启动与信任**:新团队无历史、自述技能不准时,智能派活如何降级(如先"AI 解释为何推荐"而非"AI 替你定")?信任崩塌的护栏是什么。
6. **桌面宠物的形态与边界**:仅入口对话,还是常驻陪伴 + 主动打扰的尺度?
7. **L2 可做领域的边界**:哪些"数字可交付物"AI 现实可做(文档 / 分析 / 代码)、哪些必须人?

### WorkHub 的"护城河"(opencode 也没解决,这是真·新东西)
- **多用户工作流 + 审批路由 + RBAC**:谁该批、按角色路由、审批超时 SLA、按身份审计。
- **业务对象的状态 + 合并 / 冲突 + 持久产出**:多 Agent + 多人改同一条记录时的乐观锁 / 合并(= git-like 分支合并的业务版)。
- **组织级策略 + 成本治理 + 多租户编排**:中央策略、团队预算 / 配额、众多并发自治任务的优先级调度。
