# DEMO-057 验收要点：基于 workhub-app-upload.txt 的三条业务验收检查

## 结论

1. **不出现预设交付物模板字样**：Cuu 在工具调用展示与状态栏中，不得出现「文档」「结构化数据」「小型代码」等预设交付物模板字段。
2. **必须显式引用项目网盘文件**：Cuu 提出的澄清问题中，须至少一次明确提及 `workhub-app-upload.txt`，证明已读取并理解该需求材料。
3. **澄清问题聚焦业务口径**：Cuu 的澄清问题必须围绕「谁来验收」「什么算通过」「还缺什么」三类方向之一，确保非技术审阅者能直接判断。

## 依据

- **来源文件**：`project/workhub-app-upload.txt`（项目网盘需求材料）
- **用户澄清回答**（已纳入执行范围）：「验收同学主要是项目负责人和产品验收同学，请用业务可验收、可复核的口径输出。」

该需求材料明确记载：

> 用户希望 Cuu 像 Codex/Claude Code plan mode 一样，先阅读项目网盘文件和用户输入，隐藏思考内容，只展示工具调用与当前状态，然后提出一个针对性澄清问题。

并列出三项验收重点：不得出现预设模板字段、必须提及 workhub-app-upload.txt、问题须围绕输出受众/验收口径/缺失材料。三条结论与上述验收重点一一对应。

## 详细内容

### 验收要点 1：不出现预设交付物模板字样

| 项目 | 内容 |
|------|------|
| **业务含义** | 产品验收同学只需在 Cuu 对外展示的文字中搜索关键词，无需理解技术细节 |
| **检查方式** | 全文搜索「文档」「结构化数据」「小型代码」「预设模板」四个词，任一出现即为不通过 |
| **通过标准** | 四个关键词均未出现在 Cuu 的工具调用名称、状态文字和最终输出中 |
| **不通过示例** | 状态栏显示「正在生成文档…」或输出中出现「交付物类型：结构化数据」 |
| **通过示例** | 状态栏显示「正在读取 workhub-app-upload.txt…」「正在分析需求材料…」 |

### 验收要点 2：必须显式引用项目网盘文件

| 项目 | 内容 |
|------|------|
| **业务含义** | 项目负责人可据此确认 Cuu 确实读了指定文件，而非凭空作答 |
| **检查方式** | 在 Cuu 的澄清问题上下文或前置说明中查找 `workhub-app-upload.txt` 字样 |
| **通过标准** | 至少出现一次完整文件名 `workhub-app-upload.txt`，且引用语义与文件内容一致 |
| **不通过示例** | 澄清问题只说「根据需求材料…」而不点名具体文件 |
| **通过示例** | 「我已阅读项目网盘中的 workhub-app-upload.txt，确认需求是…请问…」 |

### 验收要点 3：澄清问题聚焦业务口径

| 项目 | 内容 |
|------|------|
| **业务含义** | 产品验收同学能直接判断这个问题「是不是该由我来回答」 |
| **检查方式** | 人工判定澄清问题是否属于以下三类之一：**输出受众**（给谁看？谁拍板？）、**验收口径**（什么算做完？怎么算通过？）、**缺失材料**（还缺什么文件或信息才能开工？） |
| **通过标准** | 问题明确属于上述三类之一，且与 workhub-app-upload.txt 所述需求直接相关 |
| **不通过示例** | 「你喜欢什么颜色？」「现在几点？」——与需求无关的泛泛追问 |
| **通过示例** | 「该需求中的'针对性'是指每次只问 1 个问题，还是可以一次提多个但逐条确认？」（验收口径类） |

## 未尽事项与建议

1. **澄清策略待明确**：workhub-app-upload.txt 要求「提出一个针对性澄清问题」，但未界定是单轮一次还是允许多轮追问。建议项目负责人与产品验收同学协商后补充到需求中。
2. **「隐藏思考内容」缺乏外验手段**：审阅者只能看到 Cuu 对外展示内容，无法直接验证内部推理是否真正隐藏。如需白盒验证，建议后续补充后台日志审计机制。
3. **验收责任人已明确**：根据用户澄清，验收同学为项目负责人和产品验收同学，三条要点均可由该角色逐条复核。
