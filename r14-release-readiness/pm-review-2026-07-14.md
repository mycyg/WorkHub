## 0. 一句话结论

产品的「项目群聊 + Cuu 拎活派活」骨架已经真的立起来了（观察者、行动卡、军团面板、协同会话、模式五档都真接线），
但**金链路的最后一公里在桌面端断了**（Cuu 起草的提议在群聊里点不开、审批只能去 web），而**Cuu 干活最出彩的两个瞬间
用户看不见**（观察者「正在整理」无指示、记忆引用未落地）。即将施工的 CHAT 批方向对，但**「已读 N/M」与两年前自己
定的「刻意不做已读回执」互相打脸**，建议把这份预算换成价值更高的「未读分割线」。

## 维度 1 · 核心链路顺滑度

### F1【A/B】Cuu 起草的产出在群聊里是死文本，审批必须跳去 web —— 金链路最后一公里断点

- **问题**：新用户金链路 `建项目→群聊→拎活→行动卡→跑 run→看产出→审批` 的最后两环，在桌面端点不动。
  Cuu 干完活在群聊落一张「已起草 XX · +N -M」产出卡，但卡上只有纯文字状态，**没有「看提议 / 去审批」的可点入口**；
  军团面板输出区同理，只把 proposal 深链当文字显示。用户想审批只能切到 web `/approvals`——而 web 又没有群聊，
  看不到刚才的讨论上下文。这是桌面（主战场）金链路的硬断点，也是最刺眼的双端割裂。
- **证据**：
  - `apps/desktop-webview/src/workbench/chat/render.ts:413-414`：产出卡状态文案「已生成变更申请，等待人工确认后采纳。**提议详情页由后续批次接入这个窗口**。」
  - `apps/desktop-webview/src/workbench/army/render.ts:167`：军团输出行「深链：… **（跳转后续批次开放）**」；`css.ts:145` 同款注释。
  - web 侧确有 `/approvals` 路由（`packages/ui/src/gold-path/app-shell.ts:74`），但 web 无群聊（见 F5）。
- **建议**：优先给产出卡 + 军团输出行接上「看提议」——桌面右栏「情境面板」本就是为 diff/预览设计的（`00-interaction-design.md §1`），
  在右栏内联渲染提议 diff + 通过/打回两键（复用既有 `desktop-proposal-actions.ts` 与 web 三栏审批工作台的 VM）。
  退一步的最小版：点击深链用 `navigate` 能力拉起提议详情（哪怕先是独立视图）。
- **成本**：中（右栏内联审批=1–2 天；纯深链跳转=小时级）。**这条比 CHAT 批多数细节都更该先做**——它决定了「AI 当默认劳动力」
  的闭环能不能在主战场上真的闭合。分级 **B**（右栏内联）/ **A**（先接深链止血）。

### F2【B】观察者「正在整理刚才的讨论」指示灯从未落地 —— 60 秒静默期是「它坏了吗」的黑箱

- **问题**：交互设计明文承诺观察者触发时「Cuu 头像出现在输入区上方，微呼吸 +『正在整理刚才的讨论…』」，
  但服务端观察者 worker **不发任何「正在分析」事件**，客户端也无从得知。用户说完话、等 60 秒、突然蹦出一张行动卡——
  中间那段全黑。新用户第一反应是「是不是没生效」，老用户则完全感知不到 Cuu 在后台替他们盯着。这是「AI 干了活但用户看不见」最典型的一例。
- **证据**：
  - 承诺：`r12-desktop-workbench/00-interaction-design.md §2.2`「触发中 UI：Cuu 头像…微呼吸 +『正在整理刚才的讨论…』。**不做倒计时**」。
  - 现状：`packages/contracts/src/events.ts` 只有 4 类会话 SSE 事件（message.created / message.delta / presence.typing / action_card.updated，行 85/146/175/237），**没有观察者分析态事件**；`apps/api/src/workers/conversation-observer.ts` 只 publish `action_card.updated`（行 640），不发「开始分析」。
- **建议**：观察者进入分析窗口时 publish 一个轻量 presence 事件（复用 `presence.typing` 的模式，actor=Cuu），
  桌面 composer 上方渲染「Cuu 正在整理刚才的讨论…」呼吸态（渲染函数 `renderTypingIndicatorHtml` 已现成）。
  失败/无活儿则静默淡出（设计 §2.2 三结局本就允许静默退场）。
- **成本**：小（worker 加一处 emit + 契约加一个事件类型 + 客户端消费，半天级）。因 CHAT 批本就动 presence/SSE，**可顺路进 CHAT 批**。分级 **B**（也可 A）。

### F3【B】composer 的 `#会话` / `/技能` 两个引用入口长期挂「即将上线」灰牌

- **问题**：主区与协同会话 composer 一直摆着 `@ 文件·成员`、`#会话`、`/技能` 三个 chip，但后两个是 `--soon` 灰态、点了只弹「即将上线」占位。
  引用语法是这套产品「把讨论结构化喂给 Cuu」的核心卖点之一（对标 wisp 的 `@#/`），长期半拉子会持续削弱「这产品很聪明」的第一印象。
- **证据**：`apps/desktop-webview/src/workbench/chat/render.ts:801`（chip 渲染 `--soon` + `title="即将上线"`）、`:997-1002`（`renderComingSoonPickerHtml`）。
- **建议**：`#会话` 引用其实和 SEARCH 批是同一套跨会话检索底座，**建议把「`#` 会话引用」并进 SEARCH 批一起做**（复用统一检索端点，选中即插 chip）；
  `/技能` 若短期做不了，考虑先从 composer 撤掉这个灰 chip（摆一个永远点不动的入口比不摆更伤——违背 04 手册铁律 3「不假接线」）。
- **成本**：`#` 中（搭 SEARCH）/ 撤灰 chip 小。分级 **B**。

### F4【B】注册后零引导（ONBOARD 批已立案，此处补 PM 权重）

- **问题**：所谓 onboarding 只是注册屏（`packages/ui/src/onboarding.ts` 纯登录表单），注册成功后没有任何「跟着 Cuu 做完第一件事」的引导线。
  R13 功能密度暴涨后，新用户落地即面对空工作台。注册文案已对齐新叙事（`onboarding.ts:28`「派活干活它来，审批拍板归你」，FIX#9 已修，赞），
  但落地后的第一步引导仍缺。
- **证据**：`00-plan.md §批 ONBOARD` 已确认「仓库里并不存在注册后引导页」；本轮只做了两处轻量发现性提示（资料引导语 + 个人空间空态小字，见 `r14-guidance-cluster.md`）。
- **建议**：维持 ONBOARD 批排在 CHAT 之后的既定序即可，此处只提醒 PM 权重——**它是「首次感知 AI 价值」的唯一机会**，别再往后压。
- **成本**：小中（已立案）。分级 **B**。

## 维度 2 · 双端一致性

### F5【B/C】web 完全没有群聊，是最大的能力差 —— 「在工位用 web 的人」进不了讨论现场

- **问题**：桌面是 chat-first，web 是 GitHub 式管理面（approvals/workitems/proposals/agents/cost/knowledge/skills/settings），
  **web 没有任何会话/群聊 UI**。设计上是刻意的（聊天归桌面），但 PM 视角有真实代价：一个坐在工位、只开着浏览器的成员，
  无法参与「派活拎活」发生的现场；反过来，web 用户要审批（F1）却看不到催生这份提议的讨论。两端各握半条链路。
- **证据**：web 路由别名表 `packages/ui/src/gold-path/app-shell.ts:70-99` 无 conversation/chat；`r13-final-acceptance` 明确「web 无聊天 UI（按设计）」。
- **建议**：不建议本轮就在 web 长出完整群聊（成本高、与桌面先行策略冲突）。但建议至少做一个**只读的会话镜像**——
  web 项目主页嵌一个「项目讨论」只读时间线（复用桌面 render.ts 的纯字符串渲染函数，它本就无副作用可跨端），
  让 web 用户看得到上下文、点得进提议。可发言留待 MOBILE/后续。
- **成本**：只读镜像 中；完整可发言 大。分级 **B**（只读镜像）/ **C**（可发言）。

### F6【A】头像基本是桌面独享，web 侧发现性≈0

- **问题**：AVATAR 批刚落地，但渲染点集中在桌面（聊天行/成员条/建群选人器/设置预览）；web 因为没有群聊、成员列表也稀薄，
  头像几乎无处可见。用户在 web 设置里传了头像，回到 web 却看不到它出现在任何协作场景——投入无回报感。
- **证据**：`r14-avatar.md` 记录「web 端渲染点=成员相关列表（如有）+设置预览，聊天归桌面」；web 无群聊（F5）。
- **建议**：把头像铺到 web 已有的人出现的地方——审批工作台的审批人/负责人、工单 assignee、军团 run 执行者身份、项目成员区。
  这些 VM 已带 user_id，加一个 `avatarTileHtml` 等价渲染即可（`packages/ui/src/avatar/` 已有共享组件）。
- **成本**：小（每个渲染点几行）。分级 **A/B**。

### F7【B】模式五档只在协同会话可调，主区不可调 —— 概念正确但需防「我怎么没有那个控件」的困惑

- **问题**：模式五档 chip 只在 collab 会话 composer 出现，主区群聊固定走项目治理档（设计正确，2026-07-12 纠偏拍板）。
  但两个 composer 长得几乎一样，用户在主区找不到「我的模式」chip 时会疑惑「是不是坏了 / 我权限不够」。
- **证据**：`render.ts:760-765` 主区省略 `modeChipHtml`；`:893-894` 弹层副文案已解释「主区观察者由项目治理管」，但主区本身无任何提示。
- **建议**：主区 composer 给一个极轻的静态说明（hover 或一行灰字）：「主区由项目设置统一托管，个人模式在协同会话里调」，
  把「缺控件」从「疑似 bug」变成「有意为之」。
- **成本**：小。分级 **B**（也可 A）。

## 维度 3 · AI 价值感知

### F8【B】记忆引用（信任证据）从未落地 —— Cuu「记得你说过什么」用户完全看不到

- **问题**：交互设计 §3 承诺「Cuu 的关键发言下挂『N 条记忆引用』折叠行，展开可见依据了谁说的话/哪条团队技能——
  把 user_memories/team_skills 的注入变成**可见的信任证据**」。这是 Cuu「有记忆、懂上下文」价值感最直接的呈现，
  但聊天渲染里**完全没有记忆引用**。MEM 批做的是「记忆管理面」（能治理），但「记忆在对话里被用到时露出来」是另一件事、且价值更高。
- **证据**：`grep 记忆 chat/render.ts` 无任何记忆引用渲染；MEM 批范围（`00-plan §批 MEM`）只含管理面，不含对话内引用露出。
- **建议**：Cuu 回复消息若命中了记忆/技能，附一条可折叠「依据 N 条记忆」行（数据在 agent loop 注入侧已有出处）。
  与 FEEDBACK 批（好评差评）天然同框——用户看到「Cuu 依据了 X」旁边就能点「有用/没用」，形成感知→反馈闭环。
- **成本**：中（需 turn 回传命中的记忆 id）。分级 **B**。

### F9【B】军团/行动卡的「成本、代号、进度」是价值放大器，确认它们真的显眼

- **问题（偏肯定+提醒）**：产品把「军团有名字/实报成本/阶段流进度」都做了（`army/render.ts`、`chat/run-progress.ts` 四段阶段流），
  这是感知「AI 真在替我干活、还花了多少钱」的关键。提醒 PM：这些目前只在**右栏军团面板**和行动卡展开态里，
  主消息流只在终局冒一条摘要。对不常展开右栏的用户，价值会被埋。
- **证据**：`00-interaction-design.md §2.3`「主流里只在终局时冒一条可点摘要」；阶段流 `render.ts:177-207`。
- **建议**：不改设计克制度的前提下，考虑在行动卡的 execute 条目终局摘要里带一个极小的「花了 ¥X · 代号 阿墨」尾注，
  让成本与「谁干的」在主流里也被瞥见一眼（现在要展开面板才看得到）。
- **成本**：小。分级 **B**。

## 维度 4 · CHAT 批范围审视（编辑/删除/引用/回应/已读/在线）

**总评**：方向对，reply/reaction 是高价值低成本必做；但「已读 N/M」既与旧设计打脸又价值可疑，presence 价值偏低，
且漏了两个群聊高价值低成本项（置顶、未读分割线）。逐条：

### F10【A/B】「已读 N/M」自我打脸，且是工作群里的监视压力 —— 建议把预算换成「未读分割线」

- **问题**：CHAT 批要做「群内显示『已读 N/M』」；但同一套设计体系两年前**刻意否决过已读回执**，理由正是「不造打卡压力」。
  R14 直接反转这个决定却没给新理由。PM 判断：工作全员群里的已读回执制造「Cuu/老板知道我看了没动手」的隐性监视，
  是负价值。更糟的是**主区群聊根本没有 participant 行**（成员=工作区 membership 隐式），`conversation_participants` 也没有
  `last_read_seq` 字段——要算 N/M 得新建读游标表/惰性建行，成本不低却买来一个负价值功能。
- **证据**：
  - 反转：`00-interaction-design.md §2.1`「**刻意不做已读回执**（不造打卡压力，触达靠 attention 队列与 Cuu 气泡）」 vs `00-plan.md §批 CHAT`「群内显示『已读 N/M』」。
  - 无字段/无行：`packages/db/src/schema/core.ts:513` `conversationParticipants` 只有 id/conversationId/userId/role，无 last_read；主区成员隐式（设计 §2.1）。
- **建议**：**同一套 last_read_seq 游标，别拿去做「已读 N/M」监视回执，拿去做「未读分割线 + 跳到第一条未读」**——
  这是 Slack/Discord 的标配，纯个人视角、零监视压力，价值高得多，且正好复用你要建的读游标基础设施。
  若一定要保留触达确认，把它收窄到「只对 @ 到你的消息」或只在 1:1 协同会话，不进全员主区。
- **成本**：读游标 中（无论做哪个都要）；未读分割线的 UI 比 N/M 聚合更省。分级 **A**（决策：改用途）/ **B**（实现）。

### F11【A】漏了「置顶消息」—— 工作群最高频的低成本刚需

- **问题**：CHAT 批没有置顶。项目主区群聊里「当前目标/本周结论/那份关键文件」需要一个稳定锚点，
  否则一路刷下去就沉了。Slack/Discord/飞书/Linear 全有置顶，是群协作最省成本的高价值原语。
- **证据**：`00-plan.md §批 CHAT` 六项无置顶；聊天渲染无 pin 相关代码。
- **建议**：会话级置顶（1–3 条），顶部条常显、点击滚到原消息。数据加一列 `pinned_at`/或小表即可，与 reply 的「跳到原消息」共用滚动定位。
- **成本**：小。分级 **A**。

### F12【A】reply/引用务必自带「点引用跳到原消息」，别只做静态引用块

- **问题**：引用回复若只渲染一段被引文本、点不回原消息，价值减半（长群里找原话是主要痛点）。
- **证据**：`00-plan.md §批 CHAT` 数据模型有 `reply_to_message_id`，但未言明点击跳转；渲染层已有稳定锚点 `data-wb-chat-message-id`（`render.ts:577`）可复用。
- **建议**：引用块可点，滚动定位到 `reply_to` 目标并高亮（锚点已存在，成本极低）；被引消息删除后显示墓碑（计划已含）。
- **成本**：小。分级 **A**。

### F13【B】reaction 曝光方式与 emoji 集合建议

- **问题/建议（细节）**：
  1. **曝光**：桌面用 hover-on-message 出现的行内操作条（回应/引用/更多），别常驻按钮堆——保持「太上不知有之」的克制。触屏（未来移动端）用长按。
  2. **集合**：计划选「赞成/反对/完成/疑问/关注」语义小集合，**这个选择比 GitHub 的 8 表情更贴工作场景，赞成保留**；建议就锁死这 5 个、不开全量 picker（计划已定，支持）。
  3. **桌宠联动彩蛋**：保持 stretch/无门（计划已定）。提醒别让它拖 CHAT 批主链路。
- **证据**：`00-plan.md §批 CHAT` reaction 段 + 彩蛋段。
- **成本**：小。分级 **B**。

### F14【B】编辑/删除的下游语义要在 UI 上说清

- **问题**：编辑 15 分钟、删除不限时墓碑化（已拍板）。但「行动卡/工单已从旧文本派生、不回溯重算」这条语义，
  用户在编辑一条已被 Cuu 消化过的消息时会困惑「我改了它会重做吗」。
- **证据**：`00-plan.md §批 CHAT` 规则红线「派生物基于当时的原文，不回溯重算」。
- **建议**：编辑一条已被行动卡引用的消息时，给一句极轻提示「Cuu 已按原文拎过活，改这里不会重做已派的任务」。删除同理，墓碑文案已含（好）。
- **成本**：小。分级 **B**。

### F15【B/C】在线状态（presence）价值偏低，可降优先级

- **问题**：内部小团队不会整天挂在 app 里，在线点缀信号弱、还可能误导（显示离线其实在忙别处）。计划已把它做轻（不落库、心跳内存态），
  但仍是 CHAT 批里性价比最低的一项。
- **建议**：若 CHAT 批工期紧，presence 是第一个可砍/后置的。typing indicator（已有）已经覆盖了「有人在此刻回应」的核心信号。
- **成本**：中（相对其价值）。分级 **C**（可后置）。

## 维度 5 · 别人做得好的（便宜的小抄）

### F16【B】新增建议：主区消息级「让 Cuu 接手这条 / 变成任务」人工兜底

- **问题**：主区靠 60 秒观察者自动拎活，但观察者可能漏、或用户想立刻强制某条消息立案。目前主区没有「手动把这条交给 Cuu」的入口
  （协同会话有「变成任务/提议」，主区没有对称能力）。
- **证据**：`00-interaction-design.md §3`「会话转正：聊出来的结论一键『变成任务』」只属协同会话；主区靠观察者。
- **建议**：主区消息 hover 操作条加一项「让 Cuu 处理这条」——直接进判定/建行动卡通道（复用被 @ 必回的事件驱动直通，FIX#10 正在做）。
  既是兜底，也让「AI 拎活」从被动等待变成用户可主动触发，价值感更强。
- **成本**：小中。分级 **B**。
