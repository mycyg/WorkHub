# DEMO-055 验收要点：基于 workhub-app-upload.txt 的三条验收检查

## 结论

1. **不出现预设模板字段**：Cuu 的输出（含工具调用和状态展示）中不得出现「文档」「结构化数据」「小型代码」这类预设交付物模板字段。
2. **明确引用来源文件**：Cuu 在提出澄清问题时，必须显式提及 `workhub-app-upload.txt`，以此证明已阅读并理解项目网盘中的需求材料。
3. **澄清问题聚焦关键口径**：Cuu 提出的澄清问题须围绕输出受众、验收口径或缺失材料展开，而非泛泛或无关的追问。

## 依据

三条验收要点均提炼自 `project/workhub-app-upload.txt`，该文件载明：

> 用户希望 Cuu 像 Codex/Claude Code plan mode 一样，先阅读项目网盘文件和用户输入，隐藏思考内容，只展示工具调用与当前状态，然后提出一个针对性澄清问题。

并明确指出三项验收重点：

- **「不能出现文档/结构化数据/小型代码这类预设模板」** → 验收要点 1 的来源。
- **「必须提到 workhub-app-upload.txt」** → 验收要点 2 的来源。
- **「问题要围绕输出受众、验收口径或缺失材料」** → 验收要点 3 的来源。

## 详细内容

### 验收要点 1：不出现预设模板字段

| 项目 | 内容 |
|------|------|
| 检查对象 | Cuu 在任务执行过程中展示的工具调用名称、状态文字及最终反问/交付结果 |
| 检查方式 | 人工目视审阅，全文搜索以下关键词：「文档」「结构化数据」「小型代码」「预设模板」 |
| 通过标准 | 上述关键词完全未出现在 Cuu 的对外展示内容中（思考链内部可含，但不可外显） |
| 失败示例 | 状态栏显示「正在生成文档…」或「交付物类型：小型代码」 |
| 通过示例 | 状态栏显示「正在读取 workhub-app-upload.txt…」「正在分析需求…」 |

### 验收要点 2：明确引用来源文件

| 项目 | 内容 |
|------|------|
| 检查对象 | Cuu 最终提出的澄清问题及其上下文说明 |
| 检查方式 | 人工确认澄清问题所在段落或描述中是否包含 `workhub-app-upload.txt` 字样 |
| 通过标准 | 至少出现一次对 `workhub-app-upload.txt` 的显式引用，且引用语义正确（即确实指向项目网盘中的该文件） |
| 失败示例 | 澄清问题只说「根据需求材料…」而未点名具体文件 |
| 通过示例 | 「我已阅读项目网盘中的 workhub-app-upload.txt，针对其中描述的需求，想确认…」 |

### 验收要点 3：澄清问题聚焦关键口径

| 项目 | 内容 |
|------|------|
| 检查对象 | Cuu 提出的澄清问题的语义内容 |
| 检查方式 | 人工判定该问题是否属于以下三类之一：**输出受众**（谁来看结果？）、**验收口径**（什么算通过？）、**缺失材料**（还缺什么文件/信息？） |
| 通过标准 | 问题明确落在上述三类范畴内，且与 workhub-app-upload.txt 所述需求直接相关 |
| 失败示例 | 「你更喜欢哪种颜色？」「今天是星期几？」——与需求无关的泛泛追问 |
| 通过示例 | 「该需求的验收标准中，'针对性'是指问题数量限定为 1 个，还是允许多个但必须逐条确认？」（验收口径类） |

## 未尽事项与建议

1. **澄清问题数未明确**：`workhub-app-upload.txt` 只要求「提出一个针对性澄清问题」，但未说明是否允许连环澄清或多轮对话。建议由需求方补充澄清策略（单轮 vs 多轮）。
2. **「隐藏思考内容」的可验证性**：外部审阅者无法直接检查 Cuu 是否真正隐藏了内部推理，仅能通过 UI 展示面判断。如需白盒验证，建议补充日志审计或后台检查机制。
3. **验收权责未指定**：三条验收要点需要审阅者逐条通过/驳回，但当前未指定由谁来验收。建议明确验收责任人（如产品经理、项目经理或需求发起人）。
