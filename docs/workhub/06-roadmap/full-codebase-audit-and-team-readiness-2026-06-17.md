### 2.2 🔴 18 个高危（逐条）

#### H1. Malformed/truncated LLM response throws through generate() and safelyGenerate() swallows it, wiping deterministic diff3 candidates
- **面/类**：api-merge-fusion / error-handling
- **位置**：`apps/api/src/services/merge-fusion-candidates.ts:871 (parse) -> :893 (return) -> :902-906 (catch); deterministic computed at :843`
- **问题与影响**：createLlmMergeFusionCandidateGenerator.generate() computes deterministicSupplements at line 843 (LLM-independent, guaranteed-safe, zero-cost non-overlapping diff3 merges), then at line 871 runs llmFusionResponseSchema.parse(parseJsonObject(textFromContent(response.content))). parseJsonObject does JSON.parse, which throws on empty/non-JSON/truncated model output. CONFIRMED reachable: provider content can be [] or tool_use-only (anthropic-compatible.ts:201) so textFromContent returns '' -> JSON.parse('') throws; maxTokens:1200 (line 858) can truncate JSON. The throw propagates out of generate(); safelyGenerateMergeFusionCandidates wraps the whole call in try/catch and returns [] (lines 902-906), discarding the deterministic supplements too. collaboration.ts:409-412 documents the team already hitting the sibling of this bug (zod empty-patch parse throw -> '整批融合候选(含确定性文本 diff)被静默清零') and fixed only that schema path; the JSON.parse path remains uncoupled. createLlmMergeFusionCandidateGenerator() is the default/normal generator (proposals.ts:1712), so this is the production path.
- **建议修复**：Wrap ONLY the LLM block (client.messages.create + parseJsonObject + schema.parse + candidate mapping) in its own try/catch that logs and falls back to empty LLM supplements, then always return supplementsWithTextPatchPreviews(input, [...deterministicSupplements, ...llmSupplements]). The deterministic supplements must never be discarded due to an LLM-side failure.

#### H2. Meeting-insight notifications & calendar blocks fetched as global newest-80 with no actor scope in SQL — actor's own items crowded out by the cap in multi-project deployments
- **面/类**：api-notifications / correctness
- **位置**：`packages/db/src/repositories/schedule-notify.ts:112-130 (listMeetingInsightSources); consumed at apps/api/src/services/schedule-notify-pages.ts:486,494-495 (notifications page) and 610-611 (calendar)`
- **问题与影响**：listMeetingInsightSources applies only activeProjectCondition() + status IN ('pending','confirmed'), ORDER BY createdAt DESC LIMIT 80, with zero actor/workspace/project-membership scope. canViewMeetingInsight is applied only AFTER the fetch in the service. Confirmed structurally: meetingRecords has projectId and the per-row source carries project access, so SQL scoping is feasible. If 80+ newer pending/confirmed insights exist across projects the actor cannot see, the actor's own accessible insight never enters the result set, yielding zero meeting-insight notifications AND zero meeting calendar blocks with no error. Affects two surfaces (notifications page + calendar). The dueWorkItems query in the same file (line 150-170) IS actor-scoped via submitter/claimedBy, confirming this is an oversight not by design.
- **建议修复**：Scope to the actor's accessible projects in SQL before LIMIT: pass actorUserId/workspaceId and restrict to projects where owner==actor OR same workspace (mirror canViewProjectMeetings/canViewProjectDrive), so the cap bounds the actor's candidate set. Admins can keep the global path.

#### H3. Calendar schedule-events query has no actor/tenant scope in SQL and LIMIT 160 runs before app-layer authz — actor silently loses own in-range events past the cap
- **面/类**：api-notifications / correctness
- **位置**：`packages/db/src/repositories/schedule-notify.ts:134-149 (events query); filter at apps/api/src/services/schedule-notify-pages.ts:598-604`
- **问题与影响**：The events query selects ALL scheduleEvents with endAt in [rangeStart,rangeEnd), ORDER BY endAt ASC LIMIT 160, across every user/workspace. Authorization (createdByUserId==actor OR participant OR canViewProject OR isAdmin) is applied only afterward (line 598-604). schema/core.ts:435-447 confirms scheduleEvents has createdByUserId, participantUserIdsJson, and projectId — all needed for SQL scoping. When >160 events fall in the week globally, the earliest-endAt 160 win and the actor's own later in-week events are dropped before the per-user filter, silently. The post-filter itself is present and correct, so the 'cross-tenant leak' framing in the first pass is speculative — the confirmed defect is the completeness cliff, identical in class to finding[1].
- **建议修复**：Scope events in SQL: WHERE createdByUserId = actor OR actor = ANY(participant_user_ids_json) OR projectId IN (actor-visible projects); apply LIMIT after scoping. Global path only for admins.

#### H5. Re-running createWorkItem(session_id) deletes & rewrites acceptance items non-transactionally, wiping met/unmet review state
- **面/类**：api-workitems / data-integrity
- **位置**：`packages/db/src/repositories/work-items.ts:427-443; apps/api/src/services/work-items.ts:852-854`
- **问题与影响**：Verified. updateWorkItemFromSession at 427-443 does `db.delete(workItemAcceptanceItems).where(workItemId=...)` then `db.insert(...)` as two separate statements on the bare pool `db` (no db.transaction wrapper — only restoreAcceptedDeliverable at line 605 uses one). Acceptance items are reinserted with status defaulting to 'open' (line 436). Combined with finding #1 (this path is reachable on an already-finalized item), re-submitting create-from-session with a launcher spec destroys acceptance rows already marked met/unmet/waived during review. #### H6. Non-admin login is nickname-only: knowing a nickname yields that user's session (account impersonation)
- **面/类**：chain-auth-permissions / authz
- **位置**：`apps/api/src/routes/auth.ts:38-91 (POST /identify); packages/db/src/repositories/users.ts:82-89 (getOrCreateActiveByNickname); apps/api/src/middleware/auth.ts:116-124 (issueUserCookie sets user.cookieToken)`
- **问题与影响**：Confirmed at code level. /identify resolves a non-admin purely by nickname: getOrCreateActiveByNickname (users.ts:82-89) returns the existing UserAuthRow including its stored cookieToken, then issueUserCookie (auth.ts:117) sets THAT user's signed cookie on the caller. needsSecret (auth.ts:48) is only true when the target is already admin or admin_secret is explicitly supplied; a plain non-admin nickname triggers no secret/device/passphrase check. findActiveByCookieToken then resolves the victim on subsequent requests. validateRuntimeConfig (config env.ts:266-301) enforces cookieSecret length, cookieSecure, non-* CORS, and admin-claim secret, but imposes NO per-account auth secret. Since the API serves the SPA same-origin (app.ts attachWebStatic), any internet-exposed deployment beyond a trusted LAN is full takeover of any non-admin by nickname. This is the headline structural issue.
- **建议修复**：Bind sessions to a possessed secret/device token for re-identifying an existing non-admin (mirror the admin-claim flow for all accounts), or refuse to return an existing user's cookie unless the caller already presents that user's cookie/device token. At minimum gate the nickname-only path behind an explicit setting (e.g. AUTH_TRUST_LAN) that validateRuntimeConfig forbids when appEnv==='production'.

#### H10. Admin cost dashboard double-/triple-counts by_user and by_workitem breakdowns (and their token/turn counters)
- **面/类**：chain-cost / correctness
- **位置**：`apps/api/src/pages/cost.ts:258-272 (aggregateByScope) + :316-324 (scopeId), called at :98,:100; root cause packages/cost/src/ledger.ts:42-47 (usageToLedgerEntry copies usage.workItemId/userId onto every scope entry); DB path packages/db/src/repositories/cost-ledger.ts:94-95,137-139`

#### H11. No atomic budget reservation: concurrent runs on different work items each pass the team/user budget check and collectively overshoot the cap (TOCTOU)
- **面/类**：chain-cost / concurrency
- **位置**：`apps/api/src/workers/agent-runner.ts:1146-1177 (enqueue→decideBudget→persistCreatedRunIfWorkItemIdle), :369-389 (decideBudget reads ledgerStore.usageSnapshots), packages/cost/src/decision.ts:51-63,220-228 (constrainRunBudget)`
- **问题与影响**：decideBudget reads ledgerStore.usageSnapshots (current day/team/user usage via listEntriesForScopes) then, if allowed, creates the run. So N runs enqueued near-simultaneously when the team daily budget has R remaining each read the same R, each constrainRunBudget-clamp their per-run cap to min(default,R), and all pass — collectively spending up to ~N*R against a team/user cap of R. constrainRunBudget bounds a single run, but the aggregate team/user/eval cap can be blown by an arbitrary factor under concurrency.
- **建议修复**：Reserve budget atomically at decision time: insert a provisional 'reservation' ledger entry (estimated run cost) in the same tx that creates the run and count reservations in decideRunBudget, reconciling to actuals at run finish; OR serialize per-(team/day) budget decisions with a DB advisory lock / SELECT ... FOR UPDATE on a per-scope counter row. Document the chosen guarantee.

## 4. 综合路线建议（合并排序）

**阶段 0 —— 现役代码止血（建议先做）**：B-SEC + B-LOOP + B-COST（高危里安全+正确性+成本）。这些是已上线代码里的真 bug/洞，风险可控、收益直接，不依赖大改造。

**阶段 1 —— 团队地基（XL/L，决定能否多团队用）**：
1. 真认证（SSO/OIDC 或密码）+ 账号生命周期（邀请/停用/离职）+ 首管引导取代共享 secret。
2. 多租户隔离（user↔org 成员模型、actor 租户从用户派生、所有查询加租户谓词）——**或**明确放弃多租户并删占位表。
3. RBAC（真角色模型取代 is_admin 布尔）+ 管理控制台（用户/角色/邀请/停用）。

**阶段 2 —— 生产运维**：可观测（metrics/错误追踪/就绪探针）、可靠性（演练备份+恢复含文件卷、数据导出）、安全加固（通用限流、安全头、审计覆盖+不可变+保留、依赖扫描）。

**阶段 3 —— 规模化与 AI 运维**：agent 执行抽成独立 worker 池、多副本/LB；provider 故障切换、原子预算预留、PII/注入防护。

**阶段 4 —— 协作完整度与商业化**：外发通知（邮件/web-push）、@提及/评论、全文检索、第三方集成、计费/计量、移动端。
