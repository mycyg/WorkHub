## 概要

Today every concurrent agent run reads the same committed ledger snapshot via decideRunBudget, passes the cap check, then starts — so N starts that each individually fit the team/user/day cap can collectively blow past it (read-then-start TOCTOU, H11/#163). This design adds an atomic per-(scope, period_bucket) reservation ledger: each start reserves an estimate inside a serialized transaction (counter row + SELECT…FOR UPDATE) so concurrent starts queue against the cap, reconciles the reservation to actual at finish, and releases it on failure/crash via a lease+expiry sweep — composing with the existing cost_ledger_entries + decideRunBudget flow rather than replacing it.

## 目标架构

END STATE: a new budget_reservations table holds one ACTIVE row per agent run, each carrying (scope_kind, scope_id, period_bucket, est_tokens, est_cost_cny, actual_tokens, actual_cost_cny, status, run_id, lease_expires_at). It is the single source of truth for IN-FLIGHT (authorized-but-not-yet-billed) spend; cost_ledger_entries remains the source of truth for SETTLED spend. The cap a concurrent start must respect is: committed(ledger, scope, bucket) + reserved_outstanding(reservations, scope, bucket) + this_run_estimate <= policy.max.\n\nRESERVE (atomic, at start): a new reserveRunBudget(scopeIds, estimate) runs inside ONE db.transaction. For each capped scope (user/day, team/day, team/month) it (a) takes a row lock that serializes concurrent reservers for that (scope, bucket) — either SELECT … FOR UPDATE on a per-(scope,bucket) budget_counters row, or pg_advisory_xact_lock(hashtext(scope||bucket)) when there is no counter row yet; (b) reads committed usage for the bucket (reuse listEntriesForScopes/ledgerUsageSnapshots) PLUS SUM(est_cost/est_tokens - actual) over ACTIVE reservations for the same (scope,bucket); (c) if committed+reserved+estimate would exceed the cap for ANY scope, the whole tx rolls back and the reserver gets the SAME budget_exhausted shape decideRunBudget produces today (so the 402 path in enqueue is unchanged); (d) otherwise it inserts one ACTIVE budget_reservations row per scope with the estimate and a lease_expires_at, and commits. Because all reservers for a given (scope,bucket) contend on the same lock, they serialize: the (k+1)th concurrent start that would breach the cap loses deterministically.\n\nESTIMATE choice: the per-run estimate is the run's own cap (decision.runBudget.maxTokens / maxCostCny — already computed by decideRunBudget and stored on the run as budget.max_tokens/max_cost_cny, schema agent_runs.maxTokens/maxCostCny). Reserving the worst case is conservative-correct (never lets the team exceed the cap); reconcile then refunds the unused portion at finish. This needs no new estimation model and reuses constrainRunBudget's already-shrinking per-run ceiling.\n\nRECONCILE (at complete): when a run reaches a terminal status, reconcileRunBudget(runId, actualTokens, actualCost) sets the run's reservation rows to status=SETTLED and writes actual_tokens/actual_cost from the run's final usage. The actual spend is ALREADY in cost_ledger_entries (provider usageSink billed it during the run), so reconcile does NOT re-bill — it only flips the reservation out of 'outstanding' so the held headroom is released. Outstanding = est - actual is the live overhang that future reservers must respect; once SETTLED the row contributes 0 to reserved_outstanding (committed ledger now covers it). This composes cleanly: decideRunBudget's committed read + reservations' outstanding sum never double-count the same spend.\n\nRELEASE on failure/crash (lease/expiry): reservation rows carry lease_expires_at, refreshed by the SAME heartbeat the run already emits (agent-runner heartbeatClaim path). On clean failure, the failure branch calls reconcileRunBudget with last-seen usage → SETTLED (same as success). On crash/lost-lease, a sweep reservationsReleaseExpired() (run alongside requeueExpiredClaims) flips ACTIVE rows whose lease_expires_at < now to status=EXPIRED, releasing their full estimate; any partial spend the crashed run did bill is already in the committed ledger, so releasing the estimate cannot under-count. Reservation lease TTL is set a bit longer than the run lease so a requeued (recoverable) run keeps its reservation; a dead-lettered run's reservation expires.\n\nINTEGRATION with decision flow: decideRunBudget stays pure/unchanged for the warning/critical/exhausted notice UX. The new gate is an additional atomic guard inside enqueue, between the existing decideBudget call and persistCreatedRunIfWorkItemIdle: keep decideBudget for the notice + model-route + 402 message, then reserveRunBudget for the hard atomic cap. To keep displayed remaining honest, the cost read path (routes/cost.ts:101-118, /api/pages/cost) adds reserved_outstanding into the usage shown, so the dashboard reflects in-flight holds. Curation/eval scopes are NOT reserved (they bypass production caps today and must keep doing so).

## 数据库迁移（新表/列/索引）

- New table budget_reservations(id uuid pk, run_id uuid references agent_runs(id) on delete cascade, scope_kind varchar(16) not null, scope_id varchar(128) not null, period varchar(16) not null, period_bucket varchar(16) not null, est_tokens integer not null default 0, est_cost_cny numeric(12,6) not null default 0, actual_tokens integer not null default 0, actual_cost_cny numeric(12,6) not null default 0, status varchar(16) not null default 'active', lease_expires_at timestamptz, created_at/updated_at timestamptz). Mirrors cost_ledger_entries scope columns so the same scope helpers (scopeId/rowToScope) and the same period_bucket key are reused.
- Partial unique index budget_reservations_run_scope_active_uq ON (run_id, scope_kind, scope_id, period_bucket) WHERE status='active' — at most one active reservation per run per (scope,bucket); makes the per-run reserve idempotent under retry (onConflictDoNothing), exactly like agent_runs_work_item_active_uq.
- Index budget_reservations_scope_bucket_active_idx ON (scope_kind, scope_id, period_bucket) WHERE status='active' — the SUM(est-actual) outstanding read for a (scope,bucket) is index-only and does not scan settled/expired rows.
- Index budget_reservations_lease_idx ON (status, lease_expires_at) WHERE status='active' — drives the expiry sweep, mirroring agent_runs_claim_idx.
- OPTIONAL counter-row variant (Phase 1 alt): budget_counters(scope_kind, scope_id, period_bucket pk-composite, reserved_tokens, reserved_cost_cny, updated_at) with SELECT … FOR UPDATE on the counter row to serialize reservers without advisory locks; the reservations table still records per-run detail for reconcile/audit. Decision in open_questions.
- Migration packaging: hand-author packages/db/migrations/0022_budget_reservations.sql as custom SQL (CREATE TABLE IF NOT EXISTS + CREATE INDEX/UNIQUE INDEX IF NOT EXISTS) and append a matching idx:22 entry to packages/db/migrations/meta/_journal.json — following the 0019/0020/0021 hand-written pattern. ## 风险

- Double-counting: actual spend lives in cost_ledger_entries (billed by provider mid-run) AND est lives in reservations. The invariant 'a reservation contributes only (est-actual) once active and 0 once settled' must hold exactly, using the SAME UTC period_bucket key as the ledger (ledger.ts:29 / decision.ts:306-327). A bucket-key mismatch silently over- or under-counts.
- Estimate sizing: reserving the per-run cap (worst case) is safe but can over-reserve and prematurely block legitimate starts when runs typically spend far below cap; reconcile refunds at finish, but headroom is held for the run's duration. Too-small an estimate re-opens the TOCTOU.
- Lease tuning: reservation lease TTL must exceed the run lease so a recoverable/requeued run (requeueExpiredClaims) doesn't lose its hold mid-recovery, yet must be short enough that a truly crashed run's budget is reclaimed promptly. Mis-set TTL either leaks budget (too long) or releases a still-running reservation (too short).
- Lock-contention/serialization cost: serializing every start of a busy team on one (scope,bucket) lock is the intended behavior but adds latency under burst; advisory-lock vs counter-row choice affects this. month-period team caps make the locked bucket coarse (all team runs in a month contend).
- Migration/journal hand-edit: must append _journal.json idx:22 by hand and avoid drizzle-kit generate (snapshot chain stuck at 0015). A mistake here reds main on the migration step before any logic runs.
- Atomicity of reserve + run-insert: if reservation commits but createRunIfWorkItemIdle then 409s (work item already active), the orphaned reservation must be compensated/released or it leaks held budget until lease expiry.
- Cross-store consistency: reservations live in a new repo; the queue can run with a memory queue (no persistence) in tests — the reservation store must degrade to a memory impl there or enforcement silently no-ops in non-PG paths.

## 待决策（Open Questions — 实施前/中需用户拍板）

1. Counter-row (budget_counters with SELECT…FOR UPDATE) vs advisory-lock (pg_advisory_xact_lock on scope||bucket) vs reservation-row aggregate (FOR UPDATE on the reservation rows) for the serialization primitive? Counter-row is the most index-friendly and matches the 'per-(scope,day) counter rows' option in the epic; advisory locks avoid a second table but are opaque in pg_locks. Recommend counter-row; needs user sign-off.
2. Reserve the full per-run cap (120000 tok / 5 CNY default — conservative, may over-block) or a smaller learned/typical estimate (less blocking, slightly higher residual TOCTOU risk between reserve and first bill)? Recommend full-cap-then-reconcile for correctness; confirm acceptable.
3. Should both team/day AND team/month (and user/day) be reserved atomically in the same tx, or only the tightest cap? Reserving all is correct but means a run holds 3 reservation rows and contends on 3 locks (the month bucket being coarse). Confirm scope set.
