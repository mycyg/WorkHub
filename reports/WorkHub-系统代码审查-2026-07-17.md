## 2. P0：必须先修

### P0-01 移出工作区成员并不会真正撤销访问，昵称模式还能自动加回

**类型：前后端都显示“已移出”，但认证/数据链没有闭环。**

证据：

- `apps/api/src/services/workspace-members.ts:143-172`：移出动作只软删 `workspace_membership`，未撤销会话、设备或当前身份。
- `apps/api/src/middleware/auth.ts:298-331`：找不到 membership 时，`resolveHumanActor()` 回退到默认 workspace 常量，仍构造可用 human actor。
- `apps/api/src/routes/auth.ts:154-193,205-269`：昵称 `/identify` 会调用 `ensureDefaultWorkspaceMembership()`；被移出的默认工作区成员再次识别时会被自动补回。
- `apps/api/src/routes/auth.ts:857-870`：代码库在“停用账号”路径已经有撤销全部会话/设备的实现，成员移出路径没有复用或建立等价的 workspace-scope revocation。
- `apps/api/src/auth.test.ts:1615-1628`：现有测试反而固定了“没有 membership 时回退默认 workspace”的行为。

复现路径：管理员在 Web Settings 移出默认工作区成员 B；B 保持已登录状态继续请求，或在昵称模式再次 identify。服务端仍可能把 B 解析到默认 workspace；identify 还会新建 active membership。

影响：成员列表显示“已移出”，但权限没有同步收回，属于安全假象。依赖成员移出做离职/外部协作者回收时，数据仍可能暴露。

根因：membership 同时承担租户选择与访问授权，但鉴权层仍保留“无 membership 就进入默认租户”的迁移期兜底；成员管理服务又只改 membership，没有统一的访问撤销事务。

建议：

1. 删除生产鉴权中的无 membership 默认租户回退，缺成员关系必须 fail closed。
2. 将“移出成员”设计为事务化的 access-revocation：membership、workspace-scoped session/device grant、presence、SSE 连接与审计同一业务命令协调。
3. 昵称 identify 不得无条件恢复被管理员移除的成员；需要显式邀请/恢复动作或可审计的准入规则。
4. 增加 `remove → old cookie/device token request → 403`、`remove → identify → 不自动恢复` 的真实仓库测试。

### P0-02 桌面退出或换账号后，旧账号的私有 SSE 仍可能继续进入 Cuu/系统通知

**类型：客户端有退出设计，服务端也撤销 token，但活跃推送连接没有身份切换协议。**

证据：

- `client-tauri/src-tauri/src/main.rs:484-506`：清 token 在第 491 行提前返回，没有唤醒 SSE worker；非空 token 变化也只唤醒退避等待，不会中止活跃 response pump。
- `client-tauri/src-tauri/src/sse_worker.rs:91-136`：token 只在每次建流前读取；`pump_sse_response()` 期间不监听 token generation/变化。
- `apps/api/src/sse/stream.ts:53-159`：用户只在开流前解析，流建立后没有重新验证 session/device 是否被撤销。
- `apps/api/src/routes/auth.ts:751-791`：logout 会撤销设备或会话，但不会主动终止已经建立的 SSE。
- `apps/desktop-webview/src/pet-surface.ts:1590-1619`：桌宠收到登出广播后主要切换卡片，全局 Cuu runtime 的旧流生命周期没有与身份一起销毁。

复现路径：账号 A 建立 `/api/push/stream/me` → 退出或重绑账号 B → A 仍有审批/消息/失败事件。只要旧 TCP/SSE 连接没偶然断开，Rust/桌宠可能继续接收 A 的私密事件。

影响：A 的审批、失败、会话等私密信息可显示给随后使用同一客户端的 B，构成跨账号数据泄漏。

根因：token 存储是可变的，但 SSE worker 与服务端 stream 都把身份当成“连接建立时常量”；系统没有 `identity generation`、主动 cancel 或 revocation fan-out。

建议：

1. Rust token state 增加 generation/watch channel；任何清空或变更都必须中止当前 response pump，再用新 generation 建流。
2. WebView 的 logout 必须等待服务端 logout 和 Rust 清流都成功后再切换本地身份；失败应停在可重试状态。
3. 服务端对设备/session 撤销发布连接关闭信号，或至少在 heartbeat 周期重新验证 grant。
4. 新增 A 登录→活跃流→logout→B 登录→A 事件不可达的桌面/API 集成测试。

## 3. P1：高优先级功能与数据问题

### P1-01 桌面 logout 失败仍显示完成

- `apps/desktop-webview/src/spotlight/views/settings.ts:732-771` 在 `ctx.client.logout()` 失败时 `.catch(() => undefined)`；Rust `set_client_token` 失败同样被吞且不等待，随后立即清本地 token、广播并 reload。

- 应把退出实现为有状态事务：server revoke → stream cancel → local clear → identity switch；任一步失败必须可见、可重试并带 trace id。

### P1-03 CU run 在长时间断网后永久停更

- `apps/desktop-webview/src/desktop-cuu-runtime.ts:1717-1784` 的自制 `DesktopCuuFetchEventSource` 只 `open()` 一次；EOF 不派发 error，异常也不重连。

### P1-09 “最后一名管理员”保护存在 TOCTOU 竞态

- `apps/api/src/services/workspace-members.ts:121-125,143-160,175-190`：先查询/计数特权成员，再单独 soft delete 或 update role。
- `packages/db/src/repositories/memberships.ts` 的 list、softDelete、update 也是独立操作，没有 workspace lock/serializable 事务。

两个管理员并发移出/降级对方时，都可能先看到 count=2 并同时成功，最终 workspace 没有管理员。修复需要数据库事务与 workspace 级行锁/ advisory lock，不能只在应用层再 count 一次。

### P1-10 服务重启前已持久化、但未 claim 的 queued AgentRun 不会自动恢复

- `apps/api/src/routes/agent-runs.ts:258-318`：enqueue 后的 auto-pump 只存在于当前请求进程。
- `apps/api/src/workers/agent-run-recovery.ts:77-95`：scheduler 只有在本轮 `recoverExpiredClaims()` 返回 `requeued>0` 时才调用 `runNext()`。
- 同文件 `124-133` 与 `apps/api/src/server.ts:36-37`：启动只注册 interval，不做启动时 drain。
- `packages/db/src/repositories/agent-runs.ts:453-481`：仓库本身能 claim 普通 queued run，但 scheduler 没有调用它。

进程在 enqueue 持久化后、auto-pump claim 前崩溃，重启后该 run 可永久 queued，直到另一个新请求偶然触发 pump。启动恢复应同时处理 expired claims 与既有 queued rows，并有单实例/多实例 drain ownership。

### P1-11 ProactiveIntent 在“落 intent 后、投递前”崩溃会永久去重

- `packages/db/migrations/0063_proactive_intents.sql:9-29`：行先以 `created` 写入，`suppression_key` 全局唯一。
- `packages/db/src/repositories/proactive-intents.ts:40-64`：冲突只返回 `created:false`。
- `apps/api/src/services/proactive-intents.ts:161-177`：重复 key 直接返回 duplicate；真正投递和终态更新在 `180-278` 之后。

只要进程在 insert commit 后、delivery/markStatus 前崩溃，记录永远停在 `created`；重试又被唯一键挡住。当前没有 created-intent recovery scanner。应把 `created` 当作可恢复状态，增加 lease/attempt/next_attempt_at，或使用 transactional outbox。

### P1-12 工作项依赖 DAG 的无环保证可被并发请求击穿

- `packages/db/src/repositories/project-timeline.ts:299-344`：事务内先读项目全部边并在内存判断 cycle，再 insert；没有锁住项目/边集合，也不是 serializable。

空图上并发提交 A→B 与 B→A，两事务都在自己的快照中判断无环并成功插入，最终形成环。复合唯一索引只能防重复边，不能防环。需要按 project 加 advisory lock，或 serializable+retry，并补并发集成测试。

## 4. P2：已确认的断链、可靠性与 UX 问题

### P2-01 消息 DB commit 与 Redis publish 之间没有 outbox/replay

- `apps/api/src/services/conversations.ts:1274-1321`：消息先写 DB，publish 失败只记 warn，HTTP 仍成功。
- `apps/api/src/sse/stream.ts:82-89`：服务端明确没有按 Last-Event-ID replay。
- Redis bus 是瞬时 pub/sub；连接未断但某次 publish 失败时，其它客户端不会触发 reconnect reconcile。

结果：发送者看到成功，其他在线客户端可永久漏掉该条，直到手动刷新或另一个事件触发全量重拉。应采用 transactional outbox + delivery worker，或至少持久 event log + cursor reconcile。

### P2-02 停用账号先 soft delete，再 best-effort 清理，失败后没有可重试入口

- `apps/api/src/routes/auth.ts:816-875`：先停用用户，后续凭据、会话、设备、presence 清理都是 best-effort。
- 下一次重试会因用户已被软删而 404，无法自然恢复清理；现有测试明确允许全部 cleanup 失败仍返回 200。

虽然软删用户会阻止多数后续鉴权，但会留下脏 session/device/presence 与不可验证的清理状态。应使用可重入 offboarding job/state machine，并把未完成步骤暴露给运维。

### P2-03 成员移出/改角色的安全审计失败被完全静默吞掉

- `apps/api/src/services/workspace-members.ts:161-171,192-207`：`createAuditLog(...).catch(() => {})`，没有日志、metric 或重试。
- 同仓 `apps/api/src/routes/auth.ts:140-150` 的 best-effort 安全审计/清理至少会 `console.warn`，说明这里不是统一策略。

这是直接违反 Fail Fast / Observable / Traceability 的路径。若审计允许异步，必须进入可靠 outbox；若允许主操作继续，也必须结构化告警并带 actor/workspace/entity。

### P2-04 会话 rename 已有 DB/API/本地更新，但没有跨客户端事件

- `apps/api/src/services/conversations.ts:949-988` 的 rename 明确不广播。
- `packages/db/src/repositories/conversations.ts:1991-2015` 完成持久化。
- Desktop rail 发起端只更新自己的 VM；事件枚举/contract/consumer 没有 `conversation.renamed`。

其他窗口/其他用户的 rail 会保持旧标题，直到重载。应补领域事件和所有活动 surface 的消费/对账。

### P2-05 客户端设备管理 API 完整，但没有任何产品 UI 消费

- `apps/api/src/routes/client-devices.ts:24-87` 已有注册、列表、current、按 id revoke、revoke-current。
- `packages/api-client/src/client.ts:378-388` 已有 typed methods。
- 排除 client/test 后，全仓没有 `listClientDevices/revokeClientDevice/currentClientDevice` 的 Web/Desktop 调用点。

用户无法查看或撤销丢失、旧机器的 client token。这是**后端有设计、前端没有体现**，应进入个人 Settings 的“已登录设备”。

### P2-06 Web 会话镜像没有订阅专属 SSE，却宣称会自动刷新

- `apps/web/src/browser.ts:195-198,418-449`：全局过滤 `conversation.*`，路由订阅器没有 conversation 分支。

### P2-09 首次引导的语言偏好同步失败被吞掉

`apps/web/src/browser.ts:4397-4404` 对 `updatePreferences` 使用 `.catch(() => undefined)`，仍进入产品。当前设备看似成功，换设备/重登却回退。应展示“本地已切换、云端同步失败”并可重试，不能伪装已保存。

### P2-10 头像裁剪 dialog 缺少完整键盘焦点生命周期

### P2-11 Web Chrome QA 启动错误缺少根因日志

`apps/web/src/chrome-launch.ts:86-102,120-132` 使用 `stdio:"ignore"`。Chrome 因二进制、参数、profile 错误退出时，只剩 CDP 超时。应采集有上限的 stderr、exit code 和脱敏参数，写入最终异常，避免 QA 基础设施“只报超时”。
