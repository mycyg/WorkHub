# WorkHub 7 维度系统性审查 — 综合报告

## 一、四个点名问题的直接回答

### 1. 项目群怎么"拉人"?
**唯一入口是建群那一刻的一次性多选,建成后无法再加人。** 桌面 `rail.ts` 的新建协同弹窗里勾选成员,候选来自当前工作区花名册 `workspace_members.items`(非项目专属名单)。而 `conversation_participants` 表全代码库只有两处 `insert`——`createCollab` 建群、`openOrCreateDm` 建 DM,都只在创建事务里执行一次;没有任何 `addParticipant`,`/conversations/:id/participants` 路由只有 GET 没有 POST。**最大缺口:想把新人拉进已有群,产品里唯一办法是另建一个新会话。** 且弹窗文案明写"成员邀请和权限之后在项目设置里调",但项目设置页整页只有 AI 治理内容,根本没有成员 section——一句无法兑现的承诺。

### 2. 群成员管理现状?
**"项目成员"这个概念目前不存在。** 三层数据现状:`workspace_members` 是全工作区花名册(scope 硬编码 `workspace`,全员都能被拉进任意项目的群);`conversation_participants` 是每个会话创建时冻结的快照;项目层 `ProjectHomePageVM` 只有 `owner_label`,没有成员列表字段,产品里没有任何地方能看到"这个项目有哪些人"。**管理动作几乎全断:** 工作区邀请链路(`POST /invites`→`/invites/accept`)后端真实可跑但双端零 UI 入口;移出工作区的 `memberships.softDelete` 只有 QA 脚本调用、无路由暴露;退群/移出会话、改成员角色的能力完全不存在。一旦被拉进某个群,用户无法自行退出,管理员也无法移出或降权。

### 3. 决策收件箱触发链?
**数据源(`GET /attention`)本身是健全的四源聚合**:escalations(含 budget)、memory-conflicts、approvals、proposals.listReviewableForUser(含任务计划 review)。schema 里另有 `clarification`/`knowledge_result` 两 kind 无真实生产者(死分支)。**真正的病灶在"刷新触发不统一"**:只有 approval 创建和 agent run 终态会发 `notification.created` 让桌面角标实时刷新;而 escalation、budget、sync_conflict 三类要么根本没进用户个人 topic(`escalation.opened` 只发到 workitem/admin 话题),要么进了 `/me` 流却被桌面 `shell.ts:629` 按 `event.type !== "notification.created"` 硬过滤丢弃,只能靠 30s 轮询兜底。**且轮询只更新角标数字,已打开的收件箱面板列表不会跟着重渲——用户正开着收件箱时,新决策落定角标会变但眼前卡片不出现。** 另有一处 execute 类行动卡找不到负责人时只把行标 `escalated` 却从不落 `ai_decisions` 行,导致这类失败彻底不进队列、也无恢复入口。

### 4. 军团状态?
**当前军团总览与会话情境面板都是只读展示,且实时性有系统性盲区。** 状态覆盖 AgentRunStatus 全 6 值,但视觉归并成 run/wait/done/fail 四桶,`escalated`(卡住等人拍板)和 `queued`(正常排队)同归"等待"桶,视觉上分不出谁紧急。**核心缺陷:军团情境面板对 `agent_run` 生命周期事件零 SSE 消费**——`started/step/failed/escalated` 只发到 `topics.run`/`topics.workitem`,而面板订阅的会话流唯一刷新触发器是 `action_card.updated`(仅人工决策时发出)。结果一个纯执行中、未触发任何人工决策的 run,状态会长期停在打开会话那一刻的旧快照。交互层面:总览卡片 `interactive:false` 点不动、无法跨项目下钻;军团卡/详情没有取消(abort)入口(后端 `/abort` 已实现但 UI 零调用);后台任务区契约锁死永远空且已移除渲染(真实的 pulse/proactive 系统一律不出现)。

**四问共性:后端能力普遍完整,断点集中在"前端无入口"与"事件推送到不了该刷新的那条连接"两类。**

## 二、确认发现分层列表(已去重合并,标 kind)

### 高危 [高]
1. **[missing]** 建群后无法加人——`conversation_participants` 只在创建瞬间写一次,成员集合永久冻结,拉新人只能另建会话。
2. **[ux]** 新建项目弹窗承诺"成员邀请权限之后在项目设置里调",但项目设置页整页只有 AI 治理、无任何成员入口,是无法兑现的 UI 承诺。

12. **[dataflow]** 变更编辑器合并撞真实冲突时,把所有 409 一律映射成通用"状态变了刷新看看"文案,不分支处理 `merge_conflict`,丢了 Spotlight 已有的逐冲突解决面板。

## 三、修复批建议(按"无重叠可并行"分批)

> 文件所有权原则:同一批独占一组文件,批间尽量不碰同一文件。`shell.ts`、`attention.ts` 是两处跨批热点,已在下方标注归属与串行依赖。量级:S=1-2 天 / M=3-5 天 / L=1-2 周+。

### 批 1 — 群成员 / 项目成员模型与入口(独占 conversation-participants、invites、memberships、项目设置成员区)
包含: #1 建群加人(补 POST + workspace-membership 校验 + 99 人上限)、#16 退群/移出(补 DELETE)、#14 邀请前端入口、#15 成员移出+角色更新路由、#2 项目设置补成员 section 或删弹窗承诺、#3 项目成员模型。

**量级: 补路由与入口 M;若建项目成员模型 L。**

### 批 2 — 决策事件推送链 + 收件箱刷新(独占 shell.ts、conversation-observer、human-reserved-guard、inbox/view、approval-digest)

**依赖: #8(接真实 proactive 数据源 vs 保持锁死空)需产品拍板;其余可直接做。#7 与批 2 都涉 SSE 但文件不同,可并行。**

包含: #9 E3 草案双端入口(项目主页/审批队列露 `pending_review` 计数 + 桌面起草/审批按钮)、#10 通知偏好加"Cuu 关怀消息"开关直连 `care_messages_enabled`、#24 web 项目设置补 instructions 区块、#22 补 `notificationTypeLabel` 映射、#23 同步 `MUTABLE_NOTIFICATION_TYPES`、#35 桌面静音改用标签映射、#36 开 OKR 标题只读端点或 join 进 timeline VM。
