# 团队技能夜间自学默认开启 + 管理员手动触发

- Status: implemented
- Date: 2026-09-05
- Owner: claude-code（R23 P3b，侦察报告 A 的 SA-06）

## Problem

README 承诺「差评会真实进入夜间技能自学的反例池」。消费逻辑确实写好了（skill-curation.ts 的反例段），
但 worker 只在 `AGENT_RUN_SKILL_CURATION_ENABLED=true` 才启动，而**默认是 false**；`.env.pilot.example`、
`docker-compose.pilot.yml`、DEPLOY.md、README 里一次都没出现过这个变量；治理路由也没有任何手动入口。

三个后果叠在一起：

1. 所有按文档自托管的部署上，这条产品承诺是断的——用户点的差评被老老实实收集了，然后没有任何人消费。
2. 用户没有任何办法发现这件事。技能页只列已有技能，从不说「这台部署根本没在攒技能」，
   空列表看上去就像「AI 没本事」而不是「这个功能没开」。
3. 就算管理员知道了，也只能改环境变量重启容器——一个每天才跑一轮的后台任务，没有任何办法催它。

## Decision

**默认翻成 true**（`packages/config/src/env.ts`），敢这么做的前提是 worker 自身已有两道兜底，
本批又补了第三道：

1. **无密钥不启动**：`server.ts` 原本只看开关，现在改看 `skillCurationAvailability()`——开关开着但
   `providerRegistry.isConfigured()` 为假时同样不启动，只打一行 `skill_curation_disabled`（`reason`
   区分是开关关的还是没配密钥）。否则无 key 的自托管每夜都会对每个工作区白跑一遍 analyze 查询、
   再被 provider 的 fail-fast 打回，只刷警告不产出。
2. **队列空闲才跑**：既有约束，未改。
3. **当日花费闸**：`BUDGET_DEFAULT_CURATION_DAILY_COST_CNY`，超额整轮跳过。既有约束，未改。

`skillCurationAvailability()` 是「今晚到底会不会跑」的**唯一判定**，三处共用（server.ts 启停、
技能页 VM、手动触发端点）——否则三处各写一份 if，很快就会出现「页面说开着、worker 其实没起」。

**技能页说实话**（新增 `TeamSkillsPageVM.curation`，必填不可选）：

- `enabled` = 开关已开 **且** 配了密钥。缺一样今晚都不会跑，那就诚实显示「未启用」，
  不要显示成「已开启，等今晚」。
- `running` = 此刻正在跑。
- `last_run_at` = 本进程记到的上一轮完成时间，记不到就是 `null` 并照实说「服务器这次启动后还没自学过」。
  **刻意不拿审计日志里「上次学到新技能的时间」冒充「上次自学时间」**——没学到东西的那些轮次同样是
  跑过的，用前者冒充后者会让「跑了但没学到」看起来像「压根没跑」。
- 字段做成**必填**：可选字段会让前端回到「没有就当没开」的猜测，那正是这一批要修掉的毛病。
  `peekSkillCurationRunState()` 只「看一眼」调度器，**绝不顺手把默认调度器建出来**——技能页每次渲染
  都会读它，而建单例会连带拉起 DB client / provider registry / 预设技能读盘。页面渲染不该有副作用。

**管理员手动触发**（`POST /api/team-skills/curate-now`，202）：

- 鉴权/防抖/未启用判定全在服务层，路由只转发。非管理员 403、进行中 409、开关关着 409、
  没配密钥 503——**「关掉了」和「没配密钥」分两个码**，运维一眼看出该改开关还是该配密钥。
- 防抖只认调度器自己的 `running` 标志，**不新建表、不另存状态**。「查 running → 起一轮」之间没有
  `await`，而 `tick()` 开头是同步置 `running=true` 的，所以单线程下两个并发请求不可能都挤进去，
  第二个必然 409；夜间定时那一轮同理会把手动触发挡在门外。
- **不等这一轮跑完再回**：一轮要逐个工作区打 LLM，HTTP 请求等不起。失败只记日志——调用方下次读
  技能页就能从 `running`/`last_run_at` 看到真实结果，不需要在这里编一个「成功」出来。
- 审计的 `entityId` 用工作区 id：这一轮覆盖整个部署的技能库（沿用夜间那轮的 `listWorkspaces` 全量
  口径），不是某一条技能。
- **按钮只在「管理员 + 已启用 + 当前没在跑」时渲染**。服务端仍然独立判定（不信前端），前端这一层
  只是不给用户送一次注定被 403/409 打回的点击——渲一个必然失败的按钮就是假入口。
  两段式确认沿用 `apps/web/src/confirm-button.ts`：手动催一轮会真的花钱打 LLM，不该是零确认的单击。

**用户可见文案一律说「AI 自学 / 总结」**，不说「蒸馏」（文案禁词门禁 `check-copy-terms.ts` 已钉死；
`data-r23-skills-curation` 是测试钩子属性，不是给用户读的，测试断言因此只扫可见文本）。

## Alternatives considered

- **保持默认 false，只补文档**：最小改动，但承诺照旧是断的——绝大多数自托管者不会去读一个从未被
  提及过的开关。被否。
- **默认 true 但不加 isConfigured 守卫**：少写一个函数，代价是无 key 部署每夜刷一遍警告日志。
  「默认开」的正当性恰恰建立在「没条件跑的时候它自己不跑」上，被否。
- **`last_run_at` 取审计日志里最近一次技能晋升/精修时间**：能跨进程重启存活，但语义是错的
  （那是「上次学到东西」不是「上次跑过」），会把「跑了但没学到」显示成「压根没跑」。被否。
- **手动触发同步等这一轮跑完再回 200**：回执更实在，但一轮要逐个工作区打 LLM，必然超时。被否。
- **防抖另建一张 `curation_runs` 表**：能跨进程去重，但本批不加迁移，且单实例假设（DEPLOY.md §7）下
  进程内标志已经够用。多实例部署时这条端点可能在两台上各起一轮——记在这里，横向扩容时一并处理。
- **手动触发端点做成幂等返回 200 + `already_running: true`**：少一个错误码，但「你的点击没起作用」
  这件事应该是显式的，压成 200 会让前端很容易忘了处理。被否。

## Consequences

- 全新部署默认会攒技能，README 那条承诺回真。既有部署显式写了 `=false` 的不受影响。
- 技能页从「只列结果」变成「也说明状态」，空列表不再被误读成「AI 没本事」。
- **任何新增的「今晚会不会跑」判断都必须去 `skillCurationAvailability()` 读**，不要在自己文件里
  再写一份 `settings.agentRun.skillCurationEnabled &&` ——那正是这次要消灭的三处不一致。
- `peekSkillCurationRunState()` 读的是**进程内**状态：多实例部署下技能页只反映接到这个请求的那台。
  单实例假设（DEPLOY.md §7）之内没问题，横向扩容前需连同上面的防抖一起改。
