## 0. 一句话结论

打包管线本身不难（tauri-action 一把梭），**真正的阻塞不在 CI 而在两处产品配置**：

1. `client-tauri/src-tauri/tauri.conf.json:16` 的 CSP `connect-src` 只放行本机回环 —— 打包后的客户端**连不上远端自托管服务器**，装了也只能连同一台机器的后端。这条不解决，"分发给自托管用户"这个目标在功能上是不成立的。

其余都是常规工程量。

### 1.5 macOS 签名 / 公证现状

`scripts/dev/build-macos-app.sh`（86 行）做的是：
- L32-35：`cargo tauri build`（除非 `WORKHUB_MACOS_BUILD_SKIP_BUILD=1`）；
- L43-46：若 `.app/Contents/_CodeSignature` 缺失，兜底 `codesign --force --deep --sign -` 重签；
- L48-52：`codesign --verify --deep --strict` 不过就非零退出；
- L54-61：`spctl -a -vvv -t exec` 仅诊断——脚本 L17-18 自己写明"ad-hoc 不是公证，`spctl` rejected 是**预期**"，只拦 `bundle format unrecognized`。

`package.json:44` 的 `qa:desktop-macos-codesign-smoke` = 该脚本 + `SKIP_BUILD=1`。**这个门禁没有接进 `pnpm lint`（见 `package.json:16` 的清单），也没有出现在 `.github/workflows/verify.yml` 的任何 job 里 —— 目前是纯手动门。**

配置侧：`tauri.conf.json:84-87`
```json
"macOS": { "infoPlist": "Info.plist", "signingIdentity": "-", "hardenedRuntime": false }
```
`Info.plist` 只有一条 `LSRequiresCarbon=false`（`tauri_scaffold.rs:206-217` 断言了这一点）。

**这两个字段跟 CI 真签名直接冲突，依据是 tauri-bundler 2.9.3 源码（已从本机 cargo registry cache 解出核对）**：

- `src/bundle/macos/sign.rs:19-44` `keychain(identity)`：给了 `APPLE_CERTIFICATE` + `APPLE_CERTIFICATE_PASSWORD` 时导入证书，**若配置里还有 `signingIdentity`，会做 `certificate_identity.contains(identity)` 校验，不匹配直接 `Err`**。配置里是 `"-"`，真 Developer ID 身份串（`Developer ID Application: XXX (TEAMID)`）通常不含 `-` → **构建报错中断**。
- `src/bundle/macos/sign.rs:68`：hardened runtime 开关直接取 `settings.macos().hardened_runtime`；当前 `false` → **Apple 公证必拒**（公证强制要求 hardened runtime）。
- `src/bundle/macos/app.rs:135-149` + `sign.rs:96-110`：公证凭据是 `APPLE_ID` + `APPLE_PASSWORD` + `APPLE_TEAM_ID` 三件套（或 `APPLE_API_KEY`/`APPLE_API_ISSUER`/`APPLE_API_KEY_PATH`）。**只给前两个不给 TEAM_ID 是 `return Err(MissingTeamId)` 硬失败**，不是"跳过公证"。
- `src/bundle/macos/app.rs:115-117`：`--no-sign` 或 `keychain()` 返回 `None` 时完全不签名 —— 而 `build-macos-app.sh` L5-9 的注释记录了真实踩坑：完全不签名的 bundle 在 Apple Silicon 上 `codesign --verify` 报错、`spctl` 报 "bundle format unrecognized"、可执行体被 AMFI `SIGKILL(137)`。**所以"无证书"路径必须保留 ad-hoc `"-"`，不能简单删掉这个字段。**

## 2. `desktop-release.yml` 设计

完整草案见同目录 `r24-S2-desktop-release.yml`（已用 PyYAML 解析验证语法可读，3 job / 4 矩阵项 / 13 步）。要点：

### 2.1 触发与并发

```yaml
on:
  push:    { tags: ["v*"] }
  workflow_dispatch:
    inputs: { dry_run(bool,默认true), draft(bool,默认true), tag_name(string) }
concurrency: { group: desktop-release-${{ github.ref }}, cancel-in-progress: false }
permissions: { contents: write }
```

- **没有 `push: branches` 也没有 `pull_request`** —— 把这个文件合进 `main` 是零风险的，在打 tag / 手动点之前它永远不跑。这是先合再验的前提。
- `cancel-in-progress: false`：发布流水线不该被后续推送打断（与 `verify.yml:8-10` 的取舍相反，那里是对的）。
- 每个 job `timeout-minutes: 60`（Rust 全量编译 + 打包，冷缓存下 macOS 交叉编译最慢）。

### 2.2 `plan` job

把 tag push 与手动 dispatch 两种入口归一成 `dry_run` / `tag` / `draft` 三个 output，顺带做参数校验（非干跑必须有 tag；tag 必须形如 `v0.2.0`）。这样四个矩阵 job 里不用各写一遍 if 表达式。tag push 一律 `draft=true` —— 人工点 Publish 才对外可见。

### 2.3 矩阵

| runner | target | 说明 |
|---|---|---|
| `macos-latest` | `aarch64-apple-darwin` | 原生 |
| `macos-latest` | `x86_64-apple-darwin` | 交叉编译（前端是纯 JS 与架构无关） |
| `windows-latest` | `x86_64-pc-windows-msvc` | |
| `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | 钉 22.04 不用 latest：glibc 越老，deb/AppImage 覆盖的发行版越广 |

`fail-fast: false` —— 一个平台炸掉不该连带杀掉另外三个已经跑了 20 分钟的构建。

### 2.4 步骤链

`checkout@v4` → Linux 系统依赖（**逐字照抄 `verify.yml:69-73`**，含它对 runner 上会 404 的 azure-cli/microsoft-prod 源的规避）→ `pnpm/action-setup@v4`(11.0.9) → `setup-node@v4`(22, cache pnpm) → `dtolnay/rust-toolchain@stable` with `targets:` → `Swatinem/rust-cache@v2`（`workspaces: client-tauri/src-tauri`，**`key: ${{ matrix.target }}` 每 target 一个缓存槽**，否则交叉编译产物互不复用会持续 miss）→ `pnpm install --frozen-lockfile` → 预构建 webview → 签名预检 → `tauri-action` → 验签门。

**预构建 webview 是刻意的重复**：`tauri.conf.json:8` 的 `beforeBuildCommand` 本来就会再跑一次 `pnpm --filter @workhub/desktop-webview build`（该脚本是 `tsc --noEmit && vite build`，见 `apps/desktop-webview/package.json:8`）。显式先跑一遍只花几秒，换来的是"前端 tsc/vite 失败"与"Rust 编译失败"在日志里分属不同步骤。

### 2.5 tauri-action 用法（已核对 v1.0.0 的 `action.yml` 与 README）

版本钉死：`tauri-apps/tauri-action@v1.0.0`（tag SHA `1deb371b0cd8bd54025b384f1cd735e725c4060f`，发布于 2026-06-29，是当前最新 major）。

```yaml
projectPath: client-tauri            # 必须是含 src-tauri 的目录，且不能被 gitignore
tauriScript: pnpm dlx @tauri-apps/cli@2.11.3
args: --target ${{ matrix.target }} ${{ env.WH_EXTRA_ARGS }}
tagName / releaseName:  干跑时留空 → 只构建 + 传 workflow artifacts，完全不碰 Release
releaseDraft: <plan 输出>
generateReleaseNotes: <非干跑时 true>   # GitHub 自己按 tag 间 commit 生成，releaseBody 被前置到其上
uploadUpdaterJson: false                # 第一阶段不接更新器，免得发一个没人能用的 latest.json
uploadWorkflowArtifacts: true
workflowArtifactNamePattern: "workhub-[version]-[platform]-[arch]-[bundle]"
releaseAssetNamePattern:  "WorkHub_[version]_[platform]_[arch][setup][ext]"
retryAttempts: 3
```

- **`tauriScript` 必须显式给**。README L179-181 写明默认是 `<包管理器> tauri`，找不到本地 CLI 时 action 会**自行安装浮动 latest 的 `@tauri-apps/cli`** —— 与 `Cargo.lock` 里钉死的 `tauri 2.11.2` 存在版本漂移风险（tauri CLI 有版本不匹配检测）。`@tauri-apps/cli@2.11.3` 确认存在（`tauri-apps/tauri` 仓库有 `@tauri-apps/cli-v2.11.3` tag），且与本机 `cargo tauri --version` 完全一致。备选方案 `cargo install tauri-cli --version 2.11.3 --locked`（`tauri-cli-v2.11.3` tag 同样存在），但要从源码编译，慢很多。
- **产物命名占位符**（README L192-201 的官方清单）：`[name] [mainBinaryName] [version] [platform] [arch] [ext] [mode] [setup] [_setup] [bundle]`。加 `[setup]` 是为了区分 NSIS 的 `-setup.exe`。
- **已知竞态**：四个矩阵 job 会并发去"找/建"同一个 tag 的 Release。这是 Tauri 官方文档示例本身的形态，靠 `retryAttempts: 3` 覆盖。若真跑时观察到建重，改法是加一个 `create-release` 前置 job（`gh release create --draft`）并给矩阵传 `releaseId` 而不是 `tagName`。

### 2.6 签名：缺失 secret 仍出产物

**macOS 预检步骤**（workflow 里注释已写全依据）：

- 三件套（`APPLE_CERTIFICATE` + `APPLE_CERTIFICATE_PASSWORD` + `APPLE_SIGNING_IDENTITY`）齐全 → 用 `jq` 生成 `client-tauri/src-tauri/tauri.release-signing.conf.json`（`{"bundle":{"macOS":{"signingIdentity":"<真身份>","hardenedRuntime":true}}}`），并把 `--config src-tauri/tauri.release-signing.conf.json` 写进 `$GITHUB_ENV` 的 `WH_EXTRA_ARGS`。
  - `--config` 的相对路径按 `projectPath` 解析（README L282 明说），故前缀是 `src-tauri/` 而不是仓库根路径。
  - 这一步同时解掉了 §1.5 的两个冲突：身份串匹配 + hardened runtime 打开。
- 公证三件套（`APPLE_ID` + `APPLE_PASSWORD` + `APPLE_TEAM_ID`）**必须同时存在**才注入环境；缺一个就一个都不注入，退回"签名但不公证"。理由是 `app.rs:144` 的 `MissingTeamId` 是硬失败。
- 完全没有证书 → 什么都不做，沿用 `tauri.conf.json` 的 ad-hoc `"-"`，产出**结构完整、可本机启动、未经公证**的 `.app`/`.dmg`。

**Windows 预检步骤**：把 base64 的 pfx 导进 `Cert:\CurrentUser\My`，取 thumbprint 生成同名 override 配置（`certificateThumbprint` + `digestAlgorithm` + `timestampUrl`）。未配置证书时脚本体内 `exit 0` 跳过。
- 坑：**GitHub 的上下文可用性表里 `secrets` 在 step 级 `if` 里不可用**（只在 `env:`/`with:` 可用），所以"有没有配证书"的判断只能放在脚本体内做，不能写进 `if` 表达式。

**Linux**：不签名（deb/rpm/AppImage 的分发签名对自托管场景收益太低）。

### 2.7 macOS 验签门

在 tauri-action 之后内联 `scripts/dev/build-macos-app.sh` L43-61 的同一套断言（`_CodeSignature` 存在 + `codesign --verify --deep --strict` + `spctl` 不得是 "bundle format unrecognized"）。

**为什么不直接调那个脚本**：脚本 L24 把路径写死成 `target/release/bundle/macos/WorkHub.app`，而带 `--target <triple>` 构建时产物实际在 `target/<triple>/release/bundle/macos/`。→ 建议给脚本加一个 `WORKHUB_MACOS_BUILD_APP_PATH` 覆盖口（S 级改动），之后这一步就能改回调脚本，消掉这份重复。**这同时也把 `qa:desktop-macos-codesign-smoke` 这个目前只存在于 `package.json:44`、从未进过任何 CI job 的门禁真正接上了 CI。**

## 3. 版本发布流程

### 3.1 `scripts/dev/release-desktop.sh <version>`（建议新增）

一条命令同步四处版本号并打 tag：

```
用法: scripts/dev/release-desktop.sh 0.2.0

  1. 校验 semver 形态；校验工作树干净；校验当前在 main
  2. 就地改四处：
       package.json                            "version"
       apps/desktop-webview/package.json        "version"
       client-tauri/src-tauri/Cargo.toml        version =
       client-tauri/src-tauri/tauri.conf.json   "version"
  3. cargo update --workspace --manifest-path client-tauri/src-tauri/Cargo.toml
       （Cargo 1.78+ 的 --workspace 只刷新工作区成员在 lock 里的版本，不动第三方依赖解析。
         本机 cargo 1.98.0 支持。不做这一步 Cargo.lock 与 Cargo.toml 会不一致 →
         --locked/--frozen 场景直接失败）
  4. git add <上面 5 个文件>            ← 严格 targeted add，绝不 git add -A
     git commit -m "release: 桌面端 v0.2.0"
     git tag -a v0.2.0 -m "WorkHub 桌面端 v0.2.0"
  5. 打印下一步：git push origin main && git push origin v0.2.0
     （脚本本身不 push —— 推送 tag 就是触发发布，必须由人显式执行）
```

## 4. 自动更新（tauri-plugin-updater）评估 —— 建议放第二阶段

### 4.1 要做的事

1. **Rust 侧**：`Cargo.toml` 加 `tauri-plugin-updater = "2"`；`main.rs` 的 builder 链（`main.rs:1913-1925` 那一段）加 `.plugin(tauri_plugin_updater::Builder::new().build())`；`capabilities/default.json` 加 `updater:default` 权限（当前该文件 `permissions` 只有两条，且 `tauri_scaffold.rs:239-242` **精确断言了这个集合** —— 改权限必须同步改测试）。
2. **密钥**：`cargo tauri signer generate` 生成 minisign 密钥对。私钥 + 口令进 GitHub secrets（`TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`），**公钥硬编码进 `tauri.conf.json` 的 `plugins.updater.pubkey`**。私钥丢了 = 所有已装客户端永久失去更新能力（只能让用户手动重装），必须离线备份。
3. **配置**：`bundle.createUpdaterArtifacts: true`；`plugins.updater.endpoints: ["https://github.com/mycyg/WorkHub/releases/latest/download/latest.json"]`。
4. **CI**：把 workflow 里的 `uploadUpdaterJson` / `uploadUpdaterSignatures` 从 `false` 翻回 `true`，并注入两个签名 secret。

### 4.2 收益与代价

- **不受 CSP 限制**：更新器走 Rust 侧 `reqwest`，不是 webview 的 fetch，所以 `tauri.conf.json:16` 那条严格 `connect-src` 不影响它。这是个好消息（也意味着它无法替代 §5 的 CSP 问题）。
- **平台限制**：Linux 端更新器**只支持 AppImage**，deb/rpm 装的用户拿不到自动更新。
- **macOS 前置条件**：ad-hoc 签名的应用做原地替换更新在实践中容易被 Gatekeeper 拦。**实际上"自动更新"和"真 Developer ID 签名 + 公证"是绑定的** —— 没有真证书就先别接更新器。
- **仓库是 PUBLIC**（`gh repo view` 确认 `visibility: PUBLIC`），Release 资产可匿名下载，端点无需鉴权，这一点省事。

**建议**：第一阶段先手动发一版、确认三平台产物真能装能跑，再评估。工作量 M，且**强依赖"是否买 Apple 开发者账号"这个决策**。

### B-1【最高】打包后的客户端连不上远端自托管服务器 —— CSP 只放行本机回环

**证据**：
- `client-tauri/src-tauri/tauri.conf.json:16`：`connect-src 'self' ipc: http://ipc.localhost http://127.0.0.1:* http://localhost:* ws://127.0.0.1:* ws://localhost:*`
- `apps/desktop-webview/src/desktop-api-base.ts:6-7` 自己写明：「网络层还有第二道闸：tauri.conf.json 的 CSP connect-src 只放行 'self' + 本机回环 + ipc —— **即使存进了非回环地址，打包后的 webview 也连不出去**」
- `apps/desktop-webview/src/desktop-offline-card.ts:67`：离线卡渲染了一个"服务器地址"输入框（`http://127.0.0.1:8787` 占位）；`desktop-api-base.ts:29-31` 也确实接受任意 http/https origin —— **UI 允许填、存储层允许存、网络层不让连**，是一个假的 affordance。
- 收紧的原因有据可查：`.agents/notes/proposed/2026-08-20-desktop-client-token-shell-storage.md:16`「本轮已做的缓解（不消除根因）：CSP `connect-src` 收敛到 `'self' + 本机回环 + ipc`，令牌即使被读到也难以经 fetch/EventSource 外泄到任意外部主机」。收紧前是 `http: https: ws: wss:`（同一份文件在 `.claude/worktrees/*/client-tauri/src-tauri/tauri.conf.json:16` 还留着旧值可对照）。

**这条不解决，"分发桌面客户端给自托管用户"在功能上不成立** —— 用户只能在跑着后端的那台机器上用客户端。

四个选项（需用户拍板）：

| 选项 | 做法 | 成本 | 代价 |
|---|---|---|---|
| (a) 放宽回旧值 | `connect-src` 改回含 `http: https: ws: wss:` | S | 把 2026-08-20 那条令牌外泄缓解整个退回 |
| (b) **只放 TLS**（推荐的快解） | `connect-src` 加 `https: wss:`，不加明文 `http:`（回环仍保留明文以便本机开发） | S | 自托管方必须上 HTTPS —— 但 `DEPLOY.md:162` 本来就规定公网暴露必须 `APP_ENV=production` + `COOKIE_SECURE=true`（需 HTTPS），口径自洽；LAN 内明文 http 的远端服务器仍连不上 |
| (c) 壳层代理通道（战略解） | webview 所有 HTTP/SSE 经 Tauri command / 自定义协议转发，CSP 保持最严 | L | 同时根治令牌明文存储（那份 agent note 的 Decision 就是这个方向），但 `desktop-cuu-runtime` 的自制 EventSource、workbench chat stream、drive 下载、头像 fetch 全要改并重验 |
| (d) 不改 | 客户端定位为"本机同机使用" | 0 | 与已拍板的产品方向冲突 |

**建议**：(b) 立刻做，解锁分发；(c) 记进 roadmap 作为战略目标。

## 6. 验证策略

### 6.1 关键规则：workflow_dispatch 必须先落到默认分支

GitHub 的规则是：**`workflow_dispatch` 事件只有在工作流文件存在于仓库默认分支时才可被触发**；`--ref` 只决定"用哪个分支上的这份文件来执行"。所以：

- 文件只在特性分支上时，`gh workflow run desktop-release.yml --ref <branch>` 会失败（找不到带 `workflow_dispatch` 触发器的工作流，HTTP 422）。
- **必须先把 `desktop-release.yml` 合进 `main`**，之后才能干跑。

这个仓库的现实条件让"先合再验"是安全且可行的：
- `main` 分支**没有分支保护**（`gh api repos/mycyg/WorkHub/branches/main/protection` → 404 Branch not protected）；
- Actions 权限是 `allowed_actions: "all"`（`gh api repos/mycyg/WorkHub/actions/permissions`），第三方 action 可用，无需先加白名单；
- 这个 workflow **没有 push/PR 触发器**，合进 main 之后在打 tag 或手动点之前不会跑任何东西，`verify.yml` 的 8 个 job 也完全不受影响。

**阶段 0 · 静态（不触发任何 Actions）**
- `python3 -c "import yaml; yaml.safe_load(open(...))"` 已做，语法可解析。
